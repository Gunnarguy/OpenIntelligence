## Q1. Document parsing: text layer vs OCR, layout and reading order, tables, headings, figures, tool evaluations, and what matters most for retrieval

### Takeaway
Every current open-source pipeline makes a per-document or per-page decision. It trusts the PDF text layer when that layer is extractable and not garbled, and OCRs only scanned pages, bitmap regions or garbled text. The benchmarks disagree on which tool is best (vendor-run and independent numbers differ by up to about 25 points). They agree that pipeline tools which skip layout, reading-order and table models are far behind. For retrieval, the evidence points to text fidelity first: OCR "semantic noise" hurts every retriever. Structure retention comes next (reading order, header and footer removal, headings, tables serialised with their headers). Visual retrieval only beats text on visually rich pages.

### Cited Findings

#### Text layer vs OCR: how current tools decide
- Marker (datalab-to/marker; marker-pdf 2.0.0 released 2026-07-20 per PyPI) describes its pipeline as follows. It extracts embedded text with pdftext in the PDF's reading order, runs layout detection, and "decide[s] per page whether the embedded text is usable; garbled or scanned pages are OCR'd by the VLM (full-page in balanced, surgically per-block in fast)". It reconstructs tables from the text layer with CPU heuristics and falls back to the VLM when confidence is low. It exposes `--force_ocr`, `--strip_existing_ocr` and `--disable_ocr`, and it removes page headers and footers by default. [primary, https://raw.githubusercontent.com/datalab-to/marker/HEAD/README.md]; version date [primary, https://pypi.org/pypi/marker-pdf/json]
- Marker's README describes Docling's default pipeline as "text layer for born-digital, OCR for image regions". [primary, https://raw.githubusercontent.com/datalab-to/marker/HEAD/README.md] Docling's own `OcrOptions` has an `OcrMode` enum with `FULL_PAGE`, which replaces the deprecated `force_full_page_ocr` flag, and a documented "bitmap area threshold". TableFormer defaults to `TableFormerMode.ACCURATE`. [primary, https://raw.githubusercontent.com/docling-project/docling/HEAD/docling/datamodel/pipeline_options.py] (docling 2.130.0 released 2026-09-22 [primary, https://pypi.org/pypi/docling/json])
- Unstructured's `auto` strategy is explicit in its code. Images get `hi_res`. PDFs get `hi_res` when table structure or image extraction is requested, otherwise `fast` when `pdf_text_extractable`, otherwise `ocr_only`. [primary, https://raw.githubusercontent.com/Unstructured-IO/unstructured/HEAD/unstructured/partition/strategies.py] (unstructured 0.27.8 released 2026-09-22 [primary, https://pypi.org/pypi/unstructured/json])
- MinerU offers `-m auto|txt|ocr` and classifies PDFs as text-based or scanned, detecting "garbled PDFs" to enable OCR. [inferred (search summary), https://opendatalab.github.io/MinerU/quick_start/] MinerU 4.0 (4.0.7 released 2026-09-23) now has four quality tiers: flash, basic, standard and advanced. Flash is "lowest quality; fastest… never default final reading quality". Plain-text files are read directly rather than parsed. [primary, https://raw.githubusercontent.com/opendatalab/MinerU/HEAD/README.md]; [primary, https://pypi.org/pypi/mineru/json]
- Text layers carry artefacts even when "extractable". Unstructured's own README sample output contains the ligature glyphs "Uniﬁed" and "conﬁgurations" (U+FB01) and the glyph placeholder "(cid:0)". [primary, https://raw.githubusercontent.com/Unstructured-IO/unstructured/HEAD/README.md] GRDB's FTS documentation warns that "fi" matches the ligature "ﬁ" only after NFKC normalisation, and that NFC and NFD forms of "aimé" may not match in SQLite FTS. [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/Documentation/FullTextSearch.md]
- Apple PDFKit (`PDFPage.string` / `attributedString`) is reported to put multi-column text "in total disorder" at times, because of its column recognition. This is weak, anecdotal evidence. [inferred (search summary), https://www.nutrient.io/blog/pdf-text-extraction-in-swift/]; [inferred (search summary), https://github.com/UrsushoribilisMusic/agentic-fleet-hub/issues/1115]

#### Apple Vision RecognizeDocumentsRequest (iOS/macOS 26)
- `RecognizeDocumentsRequest` is available on iOS, iPadOS, Mac Catalyst, macOS, tvOS and visionOS 26.0. It "scans a document and extracts different groups of text and barcodes" and yields a `DocumentObservation` whose structure is grouped "by words, lines, or paragraphs", with access to "tables and lists". [primary, https://developer.apple.com/tutorials/data/documentation/vision/recognizedocumentsrequest.json]
- `DocumentObservation.Container` exposes `text`, `paragraphs`, `lists`, `tables`, `barcodes`, `title` and `DataDetectorMatch`. `Table` exposes `rows`, `columns`, `cell(row:col:)` and `boundingRegion`. The only revision is `revision1`. [primary, https://developer.apple.com/tutorials/data/documentation/vision/documentobservation/container.json]; [primary, https://developer.apple.com/tutorials/data/documentation/vision/documentobservation/container/table.json]; [primary, https://developer.apple.com/tutorials/data/documentation/vision/recognizedocumentsrequest/revision-swift.enum.json]
- In WWDC25 session 272, Apple says the request returns "one document observation per image" with a hierarchical structure. It recognises text "in 26 languages", and lines "can be grouped into paragraphs". Word-level access "is not supported for certain languages". Tables are "a 2D array of cells", in contrast to `RecognizeTextRequest`, which returned "each cell of the table as a separate object". [primary, https://developer.apple.com/videos/play/wwdc2025/272/] (June 2025)

[primary, https://raw.githubusercontent.com/opendatalab/OmniDocBench/HEAD/README.md]
- Older OmniDocBench v1.0 (2025; superseded by v1.5 and v1.6 methodology). English text edit distance: MinerU-pipeline-2.1.1 0.072, Marker-1.7.1 0.085, Unstructured-0.17.2 0.198, Docling-2.14.0 0.416. English table TEDS: MinerU 77.4, Marker 67.6, Docling 61.3, Unstructured 0. English reading-order edit: MinerU 0.097, Marker 0.116, Unstructured 0.145, Docling 0.313. [primary, https://raw.githubusercontent.com/opendatalab/OmniDocBench/v1_0/README.md] Docling was then at 2.14 and is now at 2.130, so these Docling numbers are probably outdated.
- Where they disagree: on olmOCR-bench, Marker ranks above the MinerU pipeline (Marker's own run: 76.0 vs 72.7; AllenAI's table: 76.1 vs 75.2). On OmniDocBench v1.6, the MinerU pipeline ranks above Marker (86.47 vs 78.44). Docling's only current number (50.3) comes from a competitor's harness. [primary, https://raw.githubusercontent.com/datalab-to/marker/HEAD/README.md]; [primary, https://raw.githubusercontent.com/opendatalab/OmniDocBench/HEAD/README.md]; [primary, https://raw.githubusercontent.com/allenai/olmocr/HEAD/olmocr/bench/README.md]
- LlamaParse: the `llama_cloud_services` repo carries a "DEPRECATION NOTICE… maintained until May 1, 2026", with users told to migrate to `llama-cloud>=1.0`. The README contains no benchmark. [primary, https://raw.githubusercontent.com/run-llama/llama_cloud_services/HEAD/README.md] The last `llama-parse` release was 0.6.94 (2026-02-13); `llama-cloud` 2.16.0 was released 2026-09-08. [primary, https://pypi.org/pypi/llama-parse/json]; [primary, https://pypi.org/pypi/llama-cloud/json]

#### Tables: representations for retrieval
- Docling's chunker serialises tables into "triplet form 'row, column = value'", falling back to cell text joined with ". ". Its HybridChunker defaults to `repeat_table_header = True` ("Whether to repeat a table header if the table is chunked"). [primary, https://raw.githubusercontent.com/docling-project/docling-core/HEAD/docling_core/transforms/chunker/hierarchical_chunker.py]; [primary, https://raw.githubusercontent.com/docling-project/docling-core/HEAD/docling_core/transforms/chunker/hybrid_chunker.py]
- Unstructured keeps a `text_as_html` metadata field for tables alongside plain text. [primary, https://raw.githubusercontent.com/Unstructured-IO/unstructured/HEAD/unstructured/documents/elements.py] Marker's "chunks" output carries "the full HTML of each block". [primary, https://raw.githubusercontent.com/datalab-to/marker/HEAD/README.md]
- 2026 studies report that retrieval is "more sensitive to how tabular content is linearized" than generation is. One reports HTML tables doing worse for retrieval than Markdown or LaTeX, with Markdown and LaTeX similar. Another says embeddings are largely insensitive to row order, but ranking consistency is only about 20-30%. A third, on LLM table reasoning, reports HTML at 77.3% accuracy against 80.1% for attributed table graphs, which contradicts the HTML-is-worse finding. [inferred (search summary), https://arxiv.org/html/2604.24040]; [inferred (search summary), https://arxiv.org/pdf/2601.08444]

#### Headings, section paths, figures
- Docling's `contextualize()` is "embedding-targeted". It joins the chunk's embeddable metadata (headings, captions) with the chunk text before embedding. [primary, https://raw.githubusercontent.com/docling-project/docling-core/HEAD/docling_core/transforms/chunker/base.py]
- Docling has `do_picture_classification`, `do_picture_description` and `generate_picture_images` options, plus chart-to-table conversion. [primary, https://raw.githubusercontent.com/docling-project/docling/HEAD/docling/datamodel/pipeline_options.py]; [primary, https://raw.githubusercontent.com/docling-project/docling/HEAD/README.md] With `--use_llm`, Marker replaces images with descriptions. [primary, https://raw.githubusercontent.com/datalab-to/marker/HEAD/README.md]
- ColPali (ICLR 2025), which retrieves over page images, reached 81.3 nDCG@5 on ViDoRe. Text pipelines, including Unstructured, OCR and captioning, scored roughly 65-75. [inferred (search summary), https://arxiv.org/abs/2407.01449] Against that, "Lost in OCR Translation?" (DocEng 2025) found that "OCR-based RAG is better able to generalize to unseen documents", while vision RAG does well on documents it was fine-tuned on. It also found hybrid approaches often do best. [inferred (search summary), https://arxiv.org/abs/2505.05666]

#### What matters most downstream
- OHRBench (Dec 2024; ICCV 2025; 8,561 page images, 8,498 QA pairs) separates OCR "Semantic Noise" (recognition errors) from "Formatting Noise". It finds that no retriever or LLM is immune to semantic noise, that advanced models tolerate formatting noise better, and that errors compound from OCR to retrieval to generation. [inferred (search summary), https://arxiv.org/abs/2412.02592]
- A 2026 empirical study compares six PDF parsers (pdfminer, PyMuPDF, PyPDF2, Unstructured, pdfplumber and one more) with chunking-overlap settings on FinanceBench and TableQuest, and concludes that the choice of parser and the chunking together determine answer quality. Its numeric results were not available. [inferred (search summary), https://arxiv.org/abs/2604.12047]

### Inferences
- Measured against current practice, the app's pipeline (PDFKit text plus Vision OCR; app fact from the brief) is missing three things (confidence: medium). The first is an explicit per-page "is this text layer usable?" gate (garbled, `(cid:…)` or empty text leading to OCR), as Marker, Unstructured and MinerU have. The second is header and footer removal. The third is ligature and Unicode normalisation (NFKC) before indexing. All three are cheap and address the noise type that OHRBench finds every retriever is sensitive to.
- `RecognizeDocumentsRequest` is the only on-device Apple API that returns table cells and paragraph grouping, so it is the natural route to Docling-style `row, column = value` table serialisation on device. No published accuracy benchmark exists for it (see Gaps), so its quality relative to Docling or MinerU is unknown (confidence: low).
- The disagreement between benchmarks is large enough that "tool X is best" cannot be claimed. What can be claimed is that the systems scoring low are those without layout, reading-order and table models, such as liteparse (20-22) and Marker's own no-OCR text-layer path (43.6) (confidence: medium).

### Gaps
- There is no published accuracy evaluation of Apple Vision `RecognizeDocumentsRequest`, `RecognizeTextRequest` or PDFKit text extraction against OmniDocBench, olmOCR-bench or similar. A search turned up only anecdotal comparisons.
- There is no current Docling score from an independent harness. The v1.0 numbers use Docling 2.14 from 2025, and the olmOCR-bench number comes from Marker's harness.
- There is no LlamaParse benchmark in a primary source. It is a cloud service, so it does not apply to a local-first app anyway.
- The Chroma, NVIDIA, arXiv and ACL pages could not be fetched, so the numbers for table formats and for ColPali are from search summaries only.

## Q2. Chunking: size and overlap, semantic vs fixed or structure-aware, matching the embedder's limit, parent-child, contextual headers, idempotent ingestion, dedup

### Takeaway
Independent 2024-2026 studies converge on four points. Chunk size matters more than splitter cleverness. Structure-aware chunking (paragraphs, headings) beats fixed-size chunking, but embedding-similarity "semantic" chunking rarely justifies its cost. The best size depends on the query type (factoid: about 64-512 tokens; analytical: 512-1,024 tokens or a whole page). Prepending a heading or document context gives large, repeatable gains. For all-MiniLM-L6-v2 specifically, the model truncates at 256 word pieces and was trained on 128. Chroma's own MiniLM run found its best recall at 250-token chunks. So a 300-350-word chunk (about 390-455 tokens) is likely to be partly invisible to the vector index.

### Cited Findings

#### Chunk size and overlap
- Chroma, "Evaluating Chunking Strategies for Retrieval" (Smith & Troynikov, July 2024; citation in the repo README). [primary, https://raw.githubusercontent.com/brandonstarxel/chunking_evaluation/HEAD/README.md]
  - With `text-embedding-3-large`, RecursiveCharacterTextSplitter at 200 tokens with no overlap is "consistently high performing". It beats TokenTextSplitter across all metrics for sizes ≤400 with no overlap, with recall around 85.4-89.5%. ClusterSemanticChunker reaches recall 0.913 at 400 tokens, and at 200 tokens it has the best precision and IoU (8.0%). LLMSemanticChunker has the highest recall (0.919). OpenAI's 800-token/400-overlap default had "slightly below-average recall and the lowest scores across other metrics". [inferred (search summary), https://www.trychroma.com/research/evaluating-chunking]
  - Chroma repeated the experiments with all-MiniLM-L6-v2. TokenTextSplitter achieved the highest recall (0.824) at 250 tokens with 125 overlap, dropping to 0.771 with no overlap, which Chroma read as "for smaller context, overlapping chunks are necessary for high recall". Two independent search summaries agree on this. [inferred (search summary), https://www.trychroma.com/research/evaluating-chunking]; [inferred (search summary), https://ash-space.gitbook.io/ashspace/research/chroma-chunking]
  - The README examples (text-embedding-3-large) give fixed 1,200-character chunks recall 0.809 and IoU 0.177, and ClusterSemanticChunker(max 400) recall 0.897 and IoU 0.183. [primary, https://raw.githubusercontent.com/brandonstarxel/chunking_evaluation/HEAD/README.md] The author's undated lab notebook shows mixed effects from overlap. RecursiveCharacterTextSplitter at 400 tokens with 200 overlap reached recall 0.924 and IoC 0.197, against 0.901 and 0.235 with no overlap. A second run went the other way, 0.950 against 0.961. [primary, https://raw.githubusercontent.com/brandonstarxel/semantic-chunker/HEAD/lab_book.md]
- NVIDIA, "Finding the Best Chunking Strategy for Accurate AI Responses" (2025). It tested token chunks of 128, 256, 512, 1,024 and 2,048 with 15% overlap (15% beat 10% and 20% on FinanceBench at 1,024 tokens) against page-level chunks. Page-level chunking had the best average end-to-end accuracy, 0.648, with the lowest standard deviation, 0.107. Factoid queries did best at 256-512 tokens and analytical queries at 1,024 or more. The 128- and 2,048-token extremes underperformed. The best size varied by dataset: FinanceBench 1,024, Earnings 512, KG-RAG page-level. The embeddings were nv-embed over NeMo Retriever extraction. [inferred (search summary), https://developer.nvidia.com/blog/finding-the-best-chunking-strategy-for-accurate-ai-responses/]; [inferred (search summary), https://www.premai.io/blog/rag-chunking-strategies-the-2026-benchmark-guide/]
- "Rethinking Chunk Size for Long-Document Retrieval" (May 2025). Small chunks of 64-128 tokens are best for concise, fact-based answers: SQuAD Recall@1 peaked at 64.1% with 64 tokens. Larger chunks of 512-1,024 tokens help context-heavy sets: NewsQA peaked at 55.9% R@1 with 512 tokens. Sensitivity depends on the embedder (Stella prefers larger chunks, Snowflake smaller). [inferred (search summary), https://arxiv.org/abs/2505.21700]
- "A Systematic Analysis of Chunking Strategies for Reliable QA" (Jan 2026; SPLADE retrieval, Mistral-8B generator) finds that "overlap provides no measurable benefit and increases indexing cost". Sentence chunking is the most cost-effective, matching semantic chunking up to about 5k tokens of context, and quality falls off a "context cliff" beyond about 2.5k tokens of context. [inferred (search summary), https://arxiv.org/abs/2601.14123]
- The evidence on overlap disagrees. Chroma found that overlap helps MiniLM recall at 250 tokens (0.771 to 0.824), while its IoU metric penalises overlap. NVIDIA settled on 15%. The January 2026 study found no benefit. [inferred (search summary), https://www.trychroma.com/research/evaluating-chunking]; contradicted by [inferred (search summary), https://arxiv.org/abs/2601.14123]
- Framework defaults vary widely and are not evidence of optimality. LangChain `TextSplitter` defaults to chunk_size=4000 and chunk_overlap=200 (characters). LlamaIndex defaults to DEFAULT_CHUNK_SIZE=1024 tokens and overlap 20. Unstructured defaults to CHUNK_MAX_CHARS_DEFAULT=500 characters. [primary, https://raw.githubusercontent.com/langchain-ai/langchain/HEAD/libs/text-splitters/langchain_text_splitters/base.py]; [primary, https://raw.githubusercontent.com/run-llama/llama_index/HEAD/llama-index-core/llama_index/core/constants.py]; [primary, https://raw.githubusercontent.com/Unstructured-IO/unstructured/HEAD/unstructured/chunking/base.py]

#### Semantic vs fixed vs structure-aware
- Vectara (Qu, Tu & Bao, "Is Semantic Chunking Worth the Computational Cost?", arXiv Oct 2024, NAACL 2025 Findings) finds the costs "not justified by consistent performance gains". Semantic chunking won mainly on artificially "stitched" multi-topic documents. One reported figure is breakpoint chunker F1 81.89% against 69.45% for fixed-size on Miracl document retrieval; the summary does not say whether that was the stitched or the original variant. On natural documents, fixed-size chunking was as good or better. Answer generation was comparable (BERTScore 0.50 against 0.49 on Qasper). [inferred (search summary), https://aclanthology.org/2025.findings-naacl.114/]; [inferred (search summary), https://www.marktechpost.com/2024/11/16/this-ai-paper-from-vectara-evaluates-semantic-and-fixed-size-chunking-efficiency-and-performance-in-retrieval-augmented-generation-systems/]
- A FloTorch benchmark, reported second-hand (50 papers, 905,746 tokens), found recursive splitting at 512 tokens best at 69% end-to-end accuracy. Semantic chunking scored 54% and produced fragments averaging 43 tokens. [inferred (search summary), https://www.premai.io/blog/rag-chunking-strategies-the-2026-benchmark-guide/]
- A reproduction accepted at SIGIR 2026 (ielab) reports primary numbers on BEIR (nDCG, Jina-v3, reproduced). Fixed-size, sentence and semantic chunking land within about 0.01 of each other: SciFact 0.717/0.716/0.710, NFCorpus 0.355/0.357/0.360. Late or contextualised chunking ("Con-C") adds about 0.01-0.04 on some sets, for example TREC-COVID fixed 0.739 to 0.766. [primary, https://raw.githubusercontent.com/ielab/Reproduce-chunking-2026/HEAD/README.md]
- Large 2026 evaluations of 36 methods, 6 domains and 5 embedders report that "content-aware chunking significantly improves retrieval… over naive fixed-length splitting". The best was "Paragraph Group Chunking" (mean nDCG@5 about 0.459, P@1 about 24%, Hit@5 about 59%). Larger embedders reduce sensitivity to chunking but do not remove it. The search summaries attribute this same figure to both the arXiv 2603.06976 paper and the SIGIR "Beyond Chunk-Then-Embed" paper, a possible conflation. [inferred (search summary), https://arxiv.org/abs/2603.06976]; [inferred (search summary), https://doi.org/10.1145/3805712.3808575]
- Śmigielski et al. (May-June 2026) report that "structure-aware chunking yields higher overall retrieval effectiveness, particularly in top-K metrics, and incurs significantly lower computational costs than semantic or baseline strategies". [inferred (search summary), https://arxiv.org/abs/2606.00881]

#### Matching the chunk to the embedder (all-MiniLM-L6-v2)
- According to the model card, input "longer than 256 word pieces is truncated" and the "sequence length was limited to 128 tokens during training". [inferred (search summary), https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2] In a model-hub discussion, raising max_seq_length from 256 to 512 lowered NDCG@10 from 0.47246 to 0.46083, and 128 scored best at 0.51262 on the test used, which the summary does not name. [inferred (search summary), https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2/discussions/54]
- Docling's HybridChunker uses `sentence-transformers/all-MiniLM-L6-v2` as its default tokenizer. It sets `max_tokens` from the model's `max_seq_length`, so chunks are capped at the embedder's window by construction, and it merges undersized peers (`merge_peers=True`). [primary, https://raw.githubusercontent.com/docling-project/docling-core/HEAD/docling_core/transforms/chunker/tokenizer/huggingface.py]; [primary, https://raw.githubusercontent.com/docling-project/docling-core/HEAD/docling_core/transforms/chunker/hybrid_chunker.py]
- On tokens per word, English subword "fertility" is about 1.25 for a 32k WordPiece vocabulary and 1.30 for GPT-2 BPE, which is consistent with the brief's assumption of about 1.3. [inferred (search summary), https://aclanthology.org/2023.finnlp-1.9.pdf]
- On storage cost, the Hugging Face quantization post lists all-MiniLM-L6-v2 at 384 dimensions, which is 1,536 bytes per float32 vector. [primary, https://raw.githubusercontent.com/huggingface/blog/main/embedding-quantization.md]

#### Parent-child, small-to-big, propositions
- Dense X Retrieval (Dec 2023; EMNLP 2024) finds that proposition-level retrieval units beat sentences and passages. Average Recall@5 improved by 35% (SimCSE) and 22.5% (Contriever) for unsupervised retrievers, and by 2.4-4.5% for supervised ones (DPR, ANCE, TAS-B, GTR). [inferred (search summary), https://arxiv.org/abs/2312.06648]
- LlamaIndex's auto-merging retriever evaluation showed metrics similar to the base retriever, with a 52.5% pairwise preference for auto-merging. [inferred (search summary), https://developers.llamaindex.ai/python/examples/retrievers/auto_merging_retriever/] dsRAG's query-time "Relevant Segment Extraction" merges adjacent relevant chunks into segments. On KITE, CCH plus RSE raised the score from 4.72 to 8.42, with RSE "slightly more important than CCH". [primary, https://raw.githubusercontent.com/D-Star-AI/dsRAG/HEAD/README.md]

#### Contextual chunk headers and title chains
- Anthropic's "Contextual Retrieval" (Sep 19, 2024) prepends 50-100 tokens of LLM-generated context to each chunk before embedding and before BM25 indexing. Contextual embeddings cut the top-20 retrieval failure rate by 35% (5.7% to 3.7%). Adding contextual BM25 cut it by 49% (to 2.9%), and adding a reranker by 67% (to 1.9%). Embeddings plus BM25 beat embeddings alone, and top-20 beat top-10 and top-5. [primary, https://www.anthropic.com/engineering/contextual-retrieval]
- "Structure-Aware Semantic Chunking with Title-Chain Prefixes" (Aug 2026, 1,600 queries) uses a header split, a semantic merge and a prefix built from the document's own header hierarchy, with no LLM calls. MRR@5 rose from 0.374 to 0.463 (+23.8%), and on the answerable subset from 0.828 to 0.925. The paper warns that on/off ablations of such prefixes can mislead, because annotator kappa collapsed from 0.45 to 0.04 when the prefix was removed. [inferred (search summary), https://arxiv.org/abs/2608.00824]
- dsRAG's AutoContext (document-level and section-level chunk headers) plus RSE reached 96.6% on FinanceBench against 32% for a vanilla baseline (19% per the FinanceBench paper). The README does not isolate CCH's contribution on FinanceBench. [primary, https://raw.githubusercontent.com/D-Star-AI/dsRAG/HEAD/README.md]
- "Reconstructing Context" (ECIR 2025 workshop) compares the approaches: contextual retrieval "preserves semantic coherence more effectively but requires greater computational resources", while late chunking is more efficient but "tends to sacrifice relevance and completeness". [inferred (search summary), https://arxiv.org/abs/2504.19754]

#### Deterministic, idempotent ingestion and dedup
- LangChain's indexing API (v0.3 docs) computes a hash of "both page content and metadata" per document and records it in a `RecordManager`, in order to "avoid writing duplicated content". Its cleanup modes are `none`, `incremental` (dedups and cleans up mutations continuously), `full` and `scoped_full` (which also delete removed source documents). It warns: "Do not use with a store that has been pre-populated… independently". [primary, https://raw.githubusercontent.com/langchain-ai/langchain/v0.3/docs/docs/how_to/indexing.ipynb]
- Unstructured "ensures deterministic IDs" by hashing elements, using page number and sequence number, and remaps `parent_id` to match. [primary, https://raw.githubusercontent.com/Unstructured-IO/unstructured/HEAD/unstructured/documents/elements.py]
- Near-duplicate chunks make top-k return several copies of the same passage and reduce diversity. MinHash-LSH over shingles is the standard remedy. [inferred (search summary), https://arxiv.org/pdf/2608.13956]; [inferred (search summary), https://arxiv.org/html/2604.24334]

### Inferences
- Numbers here come from the brief: 300-350 words per chunk and 55-70 words of overlap. I have not verified them, and they assume the app's MiniLM runtime truncates at the model-card default of 256 word pieces. At 1.25-1.3 tokens per word, a chunk is about 375-455 WordPiece tokens against a usable window of about 254 (256 minus [CLS] and [SEP]), which is roughly 195-203 words. So about 32-44% of each chunk's tail never reaches the embedding. Because the stride (chunk minus overlap) is 230-295 words and exceeds the roughly 200 embedded words, about 30-95 words between consecutive chunks are embedded in no chunk's vector at all, roughly 13-32% of the text. BM25 still sees them. The overlap is also wasted for dense retrieval, since it sits in the truncated tail. (confidence: medium. It depends on the real truncation length, which the separate app verification must confirm. If the Core ML port fixes the sequence length at 128, the loss is far larger.)
- The strongest single piece of evidence for this embedder is Chroma's MiniLM rerun: best recall at 250-token chunks with 50% overlap, which is about 190-200 words. That agrees with Docling capping chunks at the embedder's own max_seq_length. Reasonable targets are therefore chunks of ≤254 WordPiece tokens, counted with the real tokenizer rather than words, and a structure-aware splitter (paragraph groups under headings). Nothing in the 2024-2026 literature supports per-library self-tuning of a semantic window as better than a structure-aware splitter at a fixed token budget (confidence: medium).
- Contextual headers (title chain or section path) are the best-evidenced cheap improvement, at +23.8% MRR@5 with no LLM calls. With MiniLM they consume the same 254-token budget, so the header plus body must fit together. Alternatively, index the header in BM25 while keeping it short for the embedding (confidence: medium).
- A parent-child design (embed small units of about 128-254 tokens, return the parent section or neighbouring segment to the generator) is the natural way to reconcile MiniLM's short window with a generator's need for context. The evidence for it is moderate: Dense X, dsRAG RSE, and a mixed auto-merging result (confidence: medium).
- Idempotent re-ingestion should key each chunk by a content hash that covers the normalised text, the chunker configuration and the embedder id. With a self-tuned per-library window, re-chunking changes every chunk hash whenever the tuned size moves. That breaks idempotence and forces a full re-embed, which is an argument against self-tuning (confidence: medium).

### Gaps
- The Chroma report's full results tables, including MiniLM IoU and precision, could not be fetched. Only a few numbers came through search summaries.
- The NVIDIA blog could not be fetched, and its embedder, datasets and date are from summaries only.
- No study was found that measures retrieval loss from MiniLM truncation on realistic 300-450-token chunks. The HF discussion's 128/256/512 comparison does not name its dataset.
- No primary evidence was found on dedup gains specific to personal document libraries.

## Q3. SQLite FTS5: tokenizers, bm25 and weights, content modes, prefix, detail, maintenance, query escaping, quality vs Lucene; plus SQLite operations for apps

### Takeaway
FTS5's built-in bm25 is textbook BM25 with hard-coded k1=1.2 and b=0.75. Two things matter for a multi-library database. Its collection statistics (N, avgdl, document frequency) always come from the whole FTS table, not from a `WHERE container_id=…` subset. And its IDF formula differs from Lucene's. Differences between BM25 variants are small in the literature. The larger quality factors are the tokenizer (stemming, diacritics, CJK), Unicode normalisation and safe query construction. Operationally, Apple's own guidance matches SQLite practice: use WAL, keep connections open, use transactions, have one writer, open write transactions with BEGIN IMMEDIATE plus a busy timeout, and avoid unnecessary fsync and heavy rewrites.

### Cited Findings

#### bm25() internals, from SQLite's source (master, VERSION 3.54.0)
- `fts5Bm25Function` sets `const double k1 = 1.2;` and `const double b = 0.75;`, neither of which is configurable. It computes a per-phrase score of `IDF * (f*(k1+1)) / (f + k1*(1 - b + b*D/avgdl))`, where f is the phrase frequency, summed across columns and multiplied by that column's weight (default 1.0). D is the total number of tokens in the row across all columns. It returns `-1.0 * score`, so lower is better. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_aux.c]
- IDF is computed as `log((N - nHit + 0.5)/(nHit + 0.5))` and floored at `1e-6` when not positive. N comes from `xRowCount`, avgdl from `xColumnTotalSize(-1)/nRow`, and nHit from `xQueryPhrase` over the table. All three are statistics for the whole table, cached once per query. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_aux.c]; [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/VERSION]
- Lucene's BM25Similarity differs. It uses the same defaults `1.2f, 0.75f`, but IDF is `log(1 + (docCount - docFreq + 0.5)/(docFreq + 0.5))`, which is always positive, avgdl is per field (`sumTotalTermFreq/docCount`), and document length is lossily encoded through `SmallFloat` into a 256-entry `LENGTH_TABLE`. [primary, https://raw.githubusercontent.com/apache/lucene/main/lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java]
- Kamphuis et al., "Which BM25 Do You Mean?" (ECIR 2020; pre-2023, possibly superseded), found "no significant effectiveness differences" among eight BM25 variants, including Lucene's approximation of document length. [inferred (search summary), https://cs.uwaterloo.ca/~jimmylin/publications/Kamphuis_etal_ECIR2020_preprint.pdf] bm25s implements the Robertson, ATIRE, BM25L, BM25+ and Lucene variants and uses "Lucene's BM25 implementation (exact version)" by default. [primary, https://raw.githubusercontent.com/xhluca/bm25s/HEAD/README.md]
- On speed and size rather than ranking quality, a 2025 benchmark (GovScape) over 500,000 pages and 10,000 real queries reports Lucene with "almost 40x higher query throughput and 5x smaller disk size" than SQLite FTS5. [inferred (search summary), https://arxiv.org/pdf/2511.11010]
- Column weights are positional arguments, for example `bm25(fts, 10.0, 1.0)` to weight a title ten times the body. The `rank` column can be configured per query or persistently. [inferred (search summary), https://www.sqlite.org/fts5.html] In the source, the weight multiplies the per-column hit count before saturation. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_aux.c]

#### Tokenizers (source-verified options)
- `unicode61` defaults to `remove_diacritics` = 1 (`FTS5_REMOVE_DIACRITICS_SIMPLE`). It also accepts 0 and 2 (`COMPLEX`) and the options `tokenchars`, `separators` and `categories`. `ascii` accepts `tokenchars` and `separators`. `porter` wraps another tokenizer, `unicode61` by default. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_tokenize.c]
- `trigram` folds case by default. `case_sensitive 1` disables folding, and `remove_diacritics` is accepted only together with case folding (the source rejects it when case-sensitive). SQLite's tests note: "LIKE and GLOB both work with case-insensitive tokenizers. Only GLOB works" with case-sensitive ones. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_tokenize.c]; [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/test/fts5trigram.test] Trigram shipped in 3.34.0 (Dec 2020), and substrings shorter than 3 characters match nothing. [inferred (search summary), https://www.sqlite.org/fts5.html]
- CJK: `unicode61` treats an unbroken run of CJK characters as a single token, so CJK substring search fails. Remedies are trigram, bigram preprocessing, or custom or ICU tokenizers; FTS5 has no built-in ICU tokenizer. [inferred (search summary), https://github.com/groue/GRDB.swift/issues/413]; [inferred (search summary), https://dev.to/omochi_dev/why-sqlite-fts5s-default-tokenizer-drops-your-japanese-substrings-and-the-one-line-fix-1k2d] GRDB supports custom FTS5 tokenizers in Swift, such as `FTS5WrapperTokenizer`, with synonym and Latin-script examples, for example matching "Grossmann" with "Großmann". [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/Documentation/FTS5Tokenizers.md]
- Normalisation: "the NFC 'aim\u{00E9}' form may not match its NFD 'aime\u{0301}' equivalent". Ligatures need NFKC, and cases such as "Encyclopædia" and "Diyarbakır" need `applyingTransform` or a custom tokenizer. [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/Documentation/FullTextSearch.md]

#### Content modes, detail, prefix, limits (source-verified)
- The content modes are `FTS5_CONTENT_NORMAL`, `NONE` (contentless), `EXTERNAL` and `UNINDEXED`. The table options are `content`, `content_rowid`, `contentless_delete`, `contentless_unindexed`, `columnsize`, `locale`, `detail`, `tokendata`, `prefix` and `tokenize`. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5Int.h]; [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_config.c] `contentless_delete=1` arrived in 3.43.0 (DELETE and INSERT OR REPLACE on contentless tables) and `contentless_unindexed=1` in 3.47.0 (it stores UNINDEXED column values), while secure-delete arrived in 3.42. [inferred (search summary), https://sqlite.org/releaselog/3_47_0.html]; [inferred (search summary), https://www.phoronix.com/news/SQLite-3.42]
- External content: the application must keep the index consistent ("if they are not, query results may be unpredictable"). The documented trigger pattern removes old rows with the special command `INSERT INTO fts(fts, rowid, …) VALUES('delete', old.rowid, old.…)`. Forum reports tie corruption to triggers that make FTS5 read the already-modified content row. `'rebuild'` regenerates the index from the content table. [inferred (search summary), https://sqlite.org/forum/info/da59bf102d7a7951740bd01c4942b1119512a86bfa1b11d4f762056c8eb7fc4e]; [inferred (search summary), https://www.sqlite.org/fts5.html] GRDB automates this with `synchronize(withTable:)`, implemented as triggers, and warns that the triggers survive dropping the FTS table unless they are dropped explicitly. [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/Documentation/FullTextSearch.md]
- `detail=full|column|none` (`FTS5_DETAIL_FULL/NONE/COLUMNS`): when detail≠full, the parser rejects multi-token phrase queries, `NEAR` and `^` initial-token queries ("fts5: %s queries are not supported (detail!=full)"), and `detail=none` also rejects column filters. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_expr.c] The option shrinks the index. [inferred (search summary), https://www.sqlite.org/fts5.html]
- Prefix indexes: `FTS5_MAX_PREFIX_INDEXES 31`. Other limits are `FTS5_MAX_TOKEN_SIZE 32768` and `FTS5_DEFAULT_NEARDIST 10`. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5Int.h] Prefix indexes (for example `prefix='2 3'`) make prefix queries such as `abc*` single lookups instead of range scans, at a cost in index size. [inferred (search summary), https://www.sqlite.org/fts5.html]
- UNINDEXED columns "contain no matchable tokens". The common multi-tenant pattern is `tenant_id = ? AND fts MATCH ?`. The alternative is to index the tenant column and use `tenant_id:69` column filters. [inferred (search summary), https://sqlite.org/forum/info/6d4023ca2a59688d73c269830fa015482a52a116444fa2fe75a624001435e637]

#### Maintenance (merge, optimize) and commands (source-verified)
- The defaults are `FTS5_DEFAULT_PAGE_SIZE 4050`, `AUTOMERGE 4`, `USERMERGE 4`, `CRISISMERGE 16`, `HASHSIZE 1 MB` and `DELETE_AUTOMERGE 10%`. The configurable keys are `pgsz`, `hashsize`, `automerge`, `usermerge`, `crisismerge`, `deletemerge`, `rank`, `secure-delete` and `insttoken`, and the special commands are `delete-all`, `rebuild`, `optimize`, `merge`, `integrity-check`, `flush` and `delete`. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_config.c]; [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_main.c]
- Automerge begins once `automerge` (4) b-trees exist on one level, doing the work in later writes. A crisis merge of all b-trees on a level happens at 16, and can make one INSERT slow. [inferred (search summary), https://www.sqlite.org/fts5.html] One issue report says an index never `optimize`d settled at "~3x its merged size". This is anecdotal. [inferred (search summary), https://github.com/The-40-Thieves/obsidian-tc/issues/929]

#### Query syntax and escaping (source-verified)
- An FTS5 bareword may contain only ASCII `0-9`, `A-Z`, `a-z`, `_`, byte 0x1A and any non-ASCII byte. [primary, https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_buffer.c] So `.`, `-`, `'`, `/`, `:` and `+` in raw user input produce syntax errors or operators, for example `fts5: syntax error near "."`. The standard fix is to double-quote each token as a string and double any embedded `"`. [inferred (search summary), https://github.com/steipete/wacli/issues/57]
- GRDB's pattern constructors (`matchingAnyTokenIn`, `matchingAllTokensIn`, `matchingAllPrefixesIn`, `matchingPhrase`) "build a valid pattern from any string, including strings provided by users", while `rawPattern` throws on invalid syntax. [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/Documentation/FullTextSearch.md]

#### SQLite operations for iOS/macOS apps
- Apple's "Reducing disk writes" says to use SQLite, Core Data or SwiftData for frequently changing data, to avoid "unnecessarily closing SQLite connections", and to "Use transactions" (atomic, consolidating writes) and indices. Use WAL mode, which enables "coalescing multiple writes to the same page, reducing SQLite's use of write barriers, and supporting multiple database read threads in parallel with a writer". `VACUUM` "may result in excessive disk writes". Avoid `fsync` and `F_FULLFSYNC`. "Most apps can use… `F_BARRIERFSYNC`", and `F_FULLFSYNC` is "a best-effort guarantee… data can still be lost in the case of sudden power loss". [primary, https://developer.apple.com/tutorials/data/documentation/xcode/reducing-disk-writes.json]
- The SQLite FAQ says SQLite "will easily do 50,000 or more INSERT statements per second… but it will only do a few dozen transactions per second", hence batch bulk inserts in one transaction. [inferred (search summary), https://sqlite.org/faq.html]
- WAL: "readers do not block writers and a writer does not block readers", but there is only one writer at a time. WAL does not work over a network filesystem, because shared memory is required. Checkpoint starvation can grow the WAL without bound if a reader is always active. [inferred (search summary), https://www.sqlite.org/wal.html] With `synchronous=NORMAL`, WAL "is safe from corruption", but the last transaction may roll back after power loss. [inferred (search summary), https://www.sqlite.org/pragma.html]
- BEGIN IMMEDIATE: a DEFERRED transaction that later upgrades to a write gets `SQLITE_BUSY` immediately, without honouring `busy_timeout`, so write transactions should start with `BEGIN IMMEDIATE`. [inferred (search summary), https://berthub.eu/articles/posts/a-brief-post-on-sqlite3-database-locked-despite-timeout/] GRDB "automatically opens all write transactions with the IMMEDIATE kind" and recommends `busyMode = .timeout(...)` for multi-process writers. [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/GRDB/Documentation.docc/DatabaseSharing.md]
- GRDB's concurrency rules: "Connect to any database file only once" (one `DatabaseQueue` or `DatabasePool` per file for the app's lifetime). "All writes performed by one DatabaseQueue or DatabasePool instance are serialized". "Mind your transactions", or invariants break and "corrupt user data". [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/GRDB/Documentation.docc/Concurrency.md]
- 0xDEAD10CC: iOS kills an app that "held on to a file lock or SQLite database lock during suspension". This is mainly a risk for databases in App Group containers. GRDB's experimental mitigation is `observesSuspensionNotifications` plus posting `Database.suspendNotification`. Persistent WAL (`SQLITE_FCNTL_PERSIST_WAL`) is needed for read-only connections to shared databases. [primary, https://raw.githubusercontent.com/groue/GRDB.swift/HEAD/GRDB/Documentation.docc/DatabaseSharing.md]; [inferred (search summary), https://mjtsai.com/blog/2025/05/15/sqlite-databases-in-app-group-containers-dont/]
- Durability on Apple platforms: macOS `fsync()` does not flush the drive cache. Apple's bundled SQLite reportedly maps `PRAGMA fullfsync` to `F_BARRIERFSYNC` (measured on macOS 12.4 in 2022; pre-2023, possibly superseded). [inferred (search summary), https://bonsaidb.io/blog/acid-on-apple/]; [inferred (search summary), https://github.com/pingdotgg/t3code/issues/13544]
- A third-party mirror of the iOS system SQLite reports version 3.51.0 on iOS 26 and 27. [inferred (search summary), https://github.com/matrix-org/matrix-rust-sdk/issues/7121] The iPhoneOS 13.0, 17.0, 18.0 and 26.0 SDK stubs for `libsqlite3` (also from a third-party mirror) export `sqlite3_auto_extension` and `sqlite3_create_module`, but not `sqlite3_load_extension` or `sqlite3_enable_load_extension`. [secondary, https://raw.githubusercontent.com/xybp888/iOS-SDKs/master/iPhoneOS26.0.sdk/usr/lib/libsqlite3.tbd]

### Inferences
- The brief says the app keeps one shared FTS5 index with a `container_id` column. Because bm25's N, avgdl and document frequency are computed over the whole FTS5 table, a library's term statistics are polluted by every other library. A term that is rare in library A but common in library B gets a depressed IDF in A. If `container_id` is UNINDEXED, every MATCH also enumerates hits from all libraries before the filter applies. There are three options. Per-library FTS5 tables (or databases) give isolation and correct statistics. Indexing a container token and filtering with column syntax fixes the scan, but still pollutes the statistics and adds a token to every row's length. The third is a custom rank function that computes statistics over the container. Only the first fully matches BM25's intent (confidence: high on the mechanism, which is in the source; medium on how much it matters in practice).
- Differences between BM25 formulas (FTS5 against Lucene) are unlikely to matter compared with tokenisation. Porter or no stemming, `remove_diacritics`, NFKC normalisation of PDF text, CJK handling and safe query escaping are where FTS5 retrieval quality is won or lost on device (confidence: medium).
- Quoting each user token is the safe escaping strategy. Wrapping the whole query as one phrase silently fails if the table is `detail=column` or `detail=none` (phrase queries are rejected there) and turns OR-recall into exact-phrase matching (confidence: high on the mechanism).
- On mobile, run `'optimize'` (or a bounded number of `'merge'` steps) after bulk imports, when idle or charging. Leaving the automerge steady state costs index size and speed, but `optimize` rewrites the whole index, which is the same class of heavy write Apple warns about for VACUUM (confidence: medium).
- System SQLite on iOS cannot load sqlite-vec dynamically; there is no `sqlite3_load_extension` in the SDK stubs. It would have to be statically compiled and registered with `sqlite3_auto_extension`, or the app would bundle its own SQLite as the SQLiteVec Swift package does (see Q4) (confidence: medium).

### Gaps
- sqlite.org was blocked, so the FTS5 documentation's exact index-size figures for `detail=column` and `detail=none`, and its precise wording on external content, could not be quoted. The source code confirms behaviour but not sizes.
- No study was found that compares the ranking quality of FTS5 bm25 against Lucene BM25 on the same corpus (BEIR or similar). The only evidence is BM25-variant equivalence (Kamphuis 2020) and a throughput and size comparison (GovScape 2025).
- There is no primary source on reusing prepared statements (for example `SQLITE_PREPARE_PERSISTENT`) on Apple platforms.
- The iOS 26/27 SQLite version (3.51.0) is from a single search summary.

## Q4. On-device vector storage: exact vs HNSW/IVF at 10^4-10^6, Apple silicon scan speed, memory mapping, quantization with rescoring, and the maturity of sqlite-vec, libSQL, VecturaKit, ObjectBox, USearch and SVDB

### Takeaway
At 10^4-10^5 vectors per library, exact brute force is the evidence-backed default: FAISS, pgvector and sqlite-vec all default to it. A 384-dimensional float32 scan is memory-bound at roughly 0.5-5 ms per query per core on Apple silicon. At 10^6 it rises to about 13-50 ms. The cheaper lever is then quantization with float rescoring (float16 at negligible cost; int8 or binary with rescoring) rather than HNSW, which costs build time, memory and deletions, and has recall that must be tuned. For all-MiniLM-L6-v2 specifically, measured retention is 90.8% for int8 without rescoring and 93.8% for binary with rescoring. Among Swift options, only USearch and ObjectBox ship mature ANN. sqlite-vec is pre-v1 but brings transactional co-location with FTS5, and VecturaKit's ANN mode is by its own account "not yet available".

### Cited Findings

#### Exact vs approximate: when each is appropriate
- FAISS guidance: for "only a few searches (say 1000-10000)… direct computation is the most efficient option". "The only index that can guarantee exact results is the IndexFlatL2 or IndexFlatIP". HNSW memory is "(d * 4 + M * 2 * 4) bytes per vector", and HNSW "does not support removing vectors". Below 1M vectors, IVF with K = 4√N to 16√N clusters needs 30K-256K training vectors. RaBitQ stores "(d/8 + 8) bytes per vector". [primary, https://raw.githubusercontent.com/wiki/facebookresearch/faiss/Guidelines-to-choose-an-index.md]
- pgvector: "By default, pgvector performs exact nearest neighbor search, which provides perfect recall". With approximate indexes, filtering "is applied after the index is scanned". At 10% selectivity with HNSW and the default `ef_search` of 40, "only 4 rows will match on average", and iterative scans (0.8.0) exist to compensate. "Sharing an approximate index between tenants means vectors from one tenant can affect recall (and speed) for other tenants". [primary, https://raw.githubusercontent.com/pgvector/pgvector/HEAD/README.md]
- The USearch README says ANN is "predominantly used when an exact brute-force search becomes too resource-intensive… typically… millions of entries". `exact=True` uses SIMD kernels, and in its Colab example the exact search took 2.54 ms against 55.3 ms for FAISS `IndexFlatL2`. [primary, https://raw.githubusercontent.com/unum-cloud/usearch/HEAD/README.md]
- A July 2026 practitioner post argues that about 1M 384-dimensional documents with low query volume can be brute-forced with one NumPy line on an M4 MacBook Pro. A related figure of about 12 ms per query appears in the summary. [inferred (search summary), https://softwaredoug.com/blog/2026/07/29/just-brute-force-embeddings]

#### Throughput on Apple silicon
- SimSIMD v6.0.0 measured single-core cosine and L2 kernel throughput on 1,536-dimensional vectors on an Apple M2 Pro: float32 29.6 GB/s, float16 14.6 GB/s, bfloat16 26.3 GB/s and int8 47.1 GB/s, against 9.2, 4.6, 4.6 and 25.8 GB/s for compiler-generated serial code. [primary, https://raw.githubusercontent.com/ashvardanian/SimSIMD/v6.0.0/README.md] On Intel Sapphire Rapids, not Apple, NumKong reports mean relative dot-product error of 0.24% for f16 and 1.8% for bf16 against a higher-precision reference. [primary, https://raw.githubusercontent.com/ashvardanian/NumKong/HEAD/README.md]
- Memory bandwidth: M4 120 GB/s, M4 Pro 273 GB/s, M4 Max 546 GB/s. The A19 Pro is reported at about 75.8 GB/s (LPDDR5X-9600 on a 64-bit bus) and the A19 at about 68 GB/s. Apple does not publish iPhone bandwidth. [inferred (search summary), https://www.apple.com/newsroom/2024/10/apple-introduces-m4-pro-and-m4-max/]; [inferred (search summary), https://wccftech.com/a19-pro-vs-a19-in-depth-specifications-differences-table/]
- sqlite-vec v0.1.0 (Aug 2024), brute force: float vectors at 3,072 and 1,536 dimensions took 214 ms and 105 ms per query, smaller dimensions under 75 ms, and 3,072-dimensional bit vectors 11 ms. The summary is ambiguous about whether these times are for the 100k-vector runs or for 1M vectors ("limitations… show at 1 million"), and the hardware is not stated. vectorlite (HNSW) is reported "3x-100x faster than sqlite-vec at the cost of lower recall". [inferred (search summary), https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html]; [inferred (search summary), https://1yefuwang1.github.io/vectorlite/markdown/news.html]
- HNSW in pure Swift (swift-hnsw, Apple Silicon, macOS 26.5.1, single-threaded, random 128-dimensional data): 10k vectors took 0.058 ms at recall@10 0.8186 with efSearch 100, and 0.160 ms at 0.9838 with efSearch 320. 50k vectors took 0.112 ms at recall 0.5515 with efSearch 100 and needed efSearch 1000 (0.946 ms) to reach 0.9730. Build ran at 8,356 vectors/s (10k) and 4,695 vectors/s (50k). Float16 is supported natively. [primary, https://raw.githubusercontent.com/1amageek/swift-hnsw/HEAD/README.md]

#### Memory mapping on iOS
- WWDC18 "iOS Memory Deep Dive" (2018; pre-2023, possibly superseded) says read-only memory-mapped files "are always going to be clean pages" and that the app footprint is "the dirty and compressed segments. Clean memory doesn't really count". [primary, https://developer.apple.com/videos/play/wwdc2018/416/]
- Apple DTS (Sep 2024) on dirty `mmap(MAP_SHARED)` pages: "Apple does not document our platforms' behaviour at this level… once the unified buffer cache (UBC) has accepted data… that data will eventually make it to disk… You have some control over this with msync and madvise". Also: "iOS doesn't implement the same 'hibernation' logic that macOS does… it's entirely possible that you may see data loss", and "iOS terminates apps instead of swapping". [primary, https://developer.apple.com/forums/thread/763058]
- USearch can serve an index "from a memory-mapped file that supports random access" (`view`), including from Swift (`index.view(path)`). [primary, https://raw.githubusercontent.com/unum-cloud/usearch/HEAD/README.md]; [primary, https://raw.githubusercontent.com/unum-cloud/usearch/HEAD/swift/README.md]

#### Quantization with rescoring
- The Hugging Face and mixedbread post (Mar 22, 2024) measured NDCG@10 on MTEB retrieval. For all-MiniLM-L6-v2 (384 dimensions): float32 41.66; int8 37.82 (90.79%, dot product with no rescoring); binary 39.07 (93.79%, with rescoring: top-100 at `rescore_multiplier` 4). The authors note that MiniLM "exhibits stronger performance on binary than on int8", possibly because of the int8 calibration data. For mxbai-embed-large-v1 (1,024 dimensions), binary retained 92.53% without rescoring and 96.45% with it, and int8 with a rescore multiplier of 4-5 retained about 99%. e5-base-v2 collapsed to 74.77% under binary. Mean speedup on CPU exact search: int8 3.66x, binary 24.76x. [primary, https://raw.githubusercontent.com/huggingface/blog/main/embedding-quantization.md]; post date [primary, https://raw.githubusercontent.com/huggingface/blog/main/_blog.yml]
- Qdrant says binary quantization gives "poorer results for small embeddings (less than 1024 dimensions)", and Weaviate compensates by over-fetching. This conflicts with the MiniLM binary-plus-rescore result above, which was obtained with float32-query rescoring. [inferred (search summary), https://qdrant.tech/articles/binary-quantization/]; [inferred (search summary), https://weaviate.io/blog/binary-quantization]; contradicted in part by [primary, https://raw.githubusercontent.com/huggingface/blog/main/embedding-quantization.md]
- USearch downcasts automatically among f64, f32, bf16, f16, the float8/float6 formats, u8, i8 and b1. i8 quantization is "only valid for cosine-like metrics" (normalise, then scale to ±127), b1 only for binary metrics, and "bf16 is recommended for modern CPUs". Once quantized, "get"-like functions cannot recover the originals, so "replicate the original vectors elsewhere". [primary, https://raw.githubusercontent.com/unum-cloud/usearch/HEAD/README.md]
- MonaVec (Aug 2026 preprint) uses 4-bit training-free quantization after a randomized Hadamard transform. Brute force reached Recall@10 0.960 on 45k 1,024-dimensional BGE-M3 vectors in 27 MB. [inferred (search summary), https://arxiv.org/abs/2606.19458]

#### sqlite-vec (status, features, iOS)
- The README says it is "a pre-v1, so expect breaking changes!". It stores float, int8 and binary vectors in `vec0` virtual tables, is pure C with no dependencies, and supports metadata, auxiliary and partition-key columns. It is a Mozilla Builders project. [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/README.md] Releases: the latest stable on PyPI is 0.1.9 (2026-03-31) and the latest alpha 0.1.10a4 (2026-05-18); the first release was 2024-04-27. [primary, https://pypi.org/pypi/sqlite-vec/json]
- vec0 metadata columns: at most 16, typed TEXT, INTEGER, FLOAT or BOOLEAN, supporting `= != > >= < <=` inside KNN queries. Partition keys: at most 4. They "pre-filter vectors during a KNN search", and the docs advise "~100s of vectors" per key value to avoid over-sharding. Auxiliary `+col` columns are stored unindexed. KNN uses `match` with `k = N` (`LIMIT` works on SQLite 3.41+), and `distance_metric=cosine` is optional. [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/site/features/vec0.md]; [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/site/features/knn.md]
- The binary-quantization guide says sqlite-vec "is (currently) brute-force only and meant to run on small devices". It shows `vec_quantize_binary()` with a float32 re-score of the coarse top 20×8. [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/site/guides/binary-quant.md] Current source on HEAD adds index types `flat()`, `rescore(...)` (bit or int8 quantizer with an oversample option; enabled by default), `diskann(...)` (enabled by default; 72 neighbours by default) and experimental `ivf` (disabled). Vectors are stored in shadow tables (`%w_chunks`) inside the same database file, and `chunk_size` defaults to 1024 and must be a multiple of 8. [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/sqlite-vec.c] According to release notes, the ANN index types first appeared in alpha releases in March 2026. [inferred (search summary), https://github.com/asg017/sqlite-vec/releases]
- iOS: "As of v0.1.2, We publish pre-compiled loadable library for both platforms". XCFramework support is listed as future work, and `SQLITE_VEC_STATIC` is available for static linking. [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/site/using/android-ios.md]; [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/site/compiling.md] The Swift binding SQLiteVec (jkrukowski; SPM, iOS 13+, `SQLiteVec.initialize()`) builds its own C target `CSQLiteVec` with `SQLITE_ENABLE_FTS5` defined. [primary, https://raw.githubusercontent.com/jkrukowski/SQLiteVec/HEAD/Package.swift]; [primary, https://raw.githubusercontent.com/jkrukowski/SQLiteVec/HEAD/README.md]
- Hybrid FTS5 and vec0 search in one SQL query with reciprocal rank fusion is documented by the sqlite-vec author (Oct 2, 2024). [inferred (search summary), https://alexgarcia.xyz/blog/2024/sqlite-vec-hybrid-search/index.html]

### Inferences
- The following arithmetic is mine, from the cited rates, for 384-dimensional vectors (1,536 B as float32, 768 B as float16, 384 B as int8, 48 B as binary). A single M2-Pro-class core at about 29.6 GB/s scans float32 at 10^4 in about 0.5 ms, 10^5 in about 5 ms and 10^6 in about 52 ms. Multi-core scans are capped by DRAM bandwidth at about 13 ms (M4, 120 GB/s) or about 20 ms (A19 Pro, about 76 GB/s) for 10^6, and float16 or int8 halve or quarter those times. A binary pre-filter over 10^6 is 48 MB, followed by rescoring a few hundred float vectors. Up to about 10^5 per library, the app's exact scan with Accelerate/BNNS (app fact from the brief) is well within interactive budgets, which is consistent with FAISS, pgvector and sqlite-vec defaults. HNSW is not needed at that scale, and it would add 4.7k-8.4k vectors/s build cost (swift-hnsw, 128-dimensional), recall tuning (0.55 at ef=100 on random 50k) and deletion complexity (confidence: medium. The BNNS/Accelerate throughput itself was not measured here).
- For MiniLM, float16 storage (half the file size, negligible dot-product error) is the lowest-risk compression. int8 or binary should only be used with a float or float16 rescoring stage, since int8 without rescoring lost about 9% NDCG@10 on MTEB for this exact model (confidence: medium).
- A per-library memory-mapped file matches Apple's clean-memory guidance only if the mapping is read-only. DTS says writeback of dirty MAP_SHARED pages is undocumented and can be lost on power loss, so updates should be written to a new file and swapped atomically rather than mutated in place (confidence: medium).
- sqlite-vec's main advantage for this app is not speed, since it is also brute force by default, but that vectors live in shadow tables of the same SQLite file as FTS5. Its costs are pre-v1 status, the need to bundle SQLite or statically register the extension on iOS, and partition-key sharding advice that fits per-library isolation (confidence: medium).

### Gaps
- No published benchmark was found for Apple Accelerate, BNNS or Metal brute-force k-NN (for example `cblas_sgemv` over 10^5-10^6 × 384) on A-series or M-series chips. The per-core numbers above come from SimSIMD on an M2 Pro, and iPhone bandwidth comes from third-party spec sheets.
- The sqlite-vec v0.1.0 benchmark tables and hardware details could not be fetched, and there are no measured numbers for sqlite-vec's new `rescore` or `diskann` modes.
- There is no independent benchmark of ObjectBox Swift HNSW or VecturaKit.
- The libSQL vector documentation could not be fetched, so its status and maturity on iOS is unknown.

## Q5. Keeping full-text and vector indexes consistent, incremental updates, re-embedding migrations, and SQLite in iCloud Drive

### Takeaway
If FTS5 and the vectors live in one SQLite file (for example vec0 shadow tables), one transaction keeps them consistent for free. Split stores need an application-level protocol, such as generation numbers recorded in SQLite together with atomic file replacement and a startup reconcile, because SQLite does not even make multi-file WAL transactions atomic. Changing the embedding model is a re-embed with dual-write, backfill, validation and cutover, and vectors from different models must never be mixed. Apple's guidance is unambiguous that "a SQLite database's store file must never be stored in iCloud" (archived design guide). Apple's current paths are CloudKit (`CKSyncEngine`, Core Data with CloudKit), with the SQLite store kept local, or iCloud Documents with mandatory file coordination for user-visible files.

### Cited Findings

#### One file vs two stores
- sqlite-vec keeps vec0 data in shadow tables (`"%w"."%w_chunks"`, and others) in the same database. [primary, https://raw.githubusercontent.com/asg017/sqlite-vec/HEAD/sqlite-vec.c] SQLite transactions are atomic within each database file. With ATTACHed databases, "if the journal_mode is WAL, then transactions continue to be atomic within each individual database file" but not across the set. [inferred (search summary), https://sqlite.org/lang_attach.html]
- Apple's primitives for split stores: `Data.WritingOptions.atomic` writes "to an auxiliary file first and then replace[s] the original". `FileManager.replaceItemAt` "ensures no data loss occurs" but only works on the same volume (use `itemReplacementDirectory`). [primary, https://developer.apple.com/tutorials/data/documentation/foundation/nsdata/writingoptions/atomic.json]; [primary, https://developer.apple.com/tutorials/data/documentation/foundation/filemanager/replaceitemat(_:withitemat:backupitemname:options:).json] "Most apps can use… F_BARRIERFSYNC" for write ordering. [primary, https://developer.apple.com/tutorials/data/documentation/xcode/reducing-disk-writes.json]
- Incremental deletes: FAISS HNSW cannot remove vectors, while hnswlib (`mark_deleted`/`replace_deleted`) and USearch (on-the-fly deletions) can. [primary, https://raw.githubusercontent.com/wiki/facebookresearch/faiss/Guidelines-to-choose-an-index.md]; [primary, https://raw.githubusercontent.com/nmslib/hnswlib/HEAD/README.md]; [primary, https://raw.githubusercontent.com/unum-cloud/usearch/HEAD/README.md]

#### Re-embedding migrations
- The standard zero-downtime approach, described by Qdrant's tutorial and 2026 practitioner write-ups, is to create the new index alongside the old one, turn on dual writes so new and updated documents embed with both models, backfill history in batches, validate on a golden query set, then switch reads atomically and drop the old index. Records embedded by the old model and mixed into the new space "corrupt search quality silently". [inferred (search summary), https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/]; [inferred (search summary), https://medium.com/google-cloud/migrating-vector-embeddings-in-production-without-downtime-8a0464af6f55] (Apr 2026); [inferred (search summary), https://tianpan.co/blog/2026/07/05/retiring-an-embedding-model-reindex-without-downtime] (Jul 2026)
- LangChain's record manager ties index contents to content hashes and warns against stores populated outside the API. [primary, https://raw.githubusercontent.com/langchain-ai/langchain/v0.3/docs/docs/how_to/indexing.ipynb]

#### Apple guidance on SQLite and iCloud
- The archived iCloud Design Guide ("iCloud Fundamentals"; retired, with revision history from 2014-2017; pre-2023, possibly superseded, though no newer Apple statement reverses it) lists among what to store in iCloud "Change log files for a SQLite database (a SQLite database's store file must never be stored in iCloud)". [primary, https://developer.apple.com/library/archive/documentation/General/Conceptual/iCloudDesignGuide/Chapters/iCloudFundametals.html]
- The same archived guide says "The use of file coordinators and presenters is mandatory when working with iCloud documents". Apps "must use file coordination to read and write the contents of files", and `UIDocument`/`NSDocument` provide it automatically. [primary, https://developer.apple.com/library/archive/documentation/General/Conceptual/iCloudDesignGuide/Chapters/DesigningForDocumentsIniCloud.html] Current `NSFileCoordinator` docs: coordinators serialise reads and writes among file presenters across processes. An app that enters the background with an active file presenter "may be terminated… to prevent deadlock", so presenters should be removed on backgrounding. [primary, https://developer.apple.com/tutorials/data/documentation/foundation/nsfilecoordinator.json]
- "The use of iCloud with Core Data has been deprecated and is no longer being supported". That older design kept the SQLite file local and synced transaction logs through the ubiquity container. [primary, https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/UsingCoreDataWithiCloudPG/Introduction/Introduction.html]
- Current Apple docs cover several points. On iOS, "iCloud doesn't synchronize the document data until an app asks (either explicitly or implicitly)", and apps discover documents with `NSMetadataQuery`. [primary, https://developer.apple.com/tutorials/data/documentation/uikit/synchronizing-documents-in-the-icloud-environment.json] `evictUbiquitousItem(at:)` removes the local copy while keeping it in iCloud, and `startDownloadingUbiquitousItem(at:)` fetches it. [primary, https://developer.apple.com/tutorials/data/documentation/foundation/filemanager/evictubiquitousitem(at:).json]; [primary, https://developer.apple.com/tutorials/data/documentation/foundation/filemanager/startdownloadingubiquitousitem(at:).json] Apple's guide to choosing iCloud storage says files go in iCloud Documents, key-value storage holds at most 1,024 keys, and model objects belong in CloudKit. [primary, https://developer.apple.com/tutorials/data/documentation/cloudkit/deciding-whether-cloudkit-is-right-for-your-app.json]
- The CloudKit alternatives. `CKSyncEngine` (iOS 17+) "manages the synchronization of local and remote record data". Its schedule is "indeterminate", depending on battery, network and account. The app must persist the engine's opaque state across launches, and it should not be used for the public database. [primary, https://developer.apple.com/tutorials/data/documentation/cloudkit/cksyncengine-4b4w9.json] `NSPersistentCloudKitContainer` (iOS 13+) "mirrors select persistent stores to a CloudKit private database". The store must be `NSSQLiteStoreType`, and CloudKit rejects unique constraints and required relationships. [primary, https://developer.apple.com/tutorials/data/documentation/coredata/nspersistentcloudkitcontainer.json]; [primary, https://developer.apple.com/tutorials/data/documentation/coredata/mirroring-a-core-data-store-with-cloudkit.json] Apple DTS (Quinn, Apr 2017; pre-2023): "store the 'truth' in iCloud (via CloudKit) and then have each device's local copy be a cache of that truth". [primary, https://developer.apple.com/forums/thread/76102]
- SQLite-side corruption risks. Copying a `.db` without its `-wal` "throws away committed data that only lives in the WAL". Moving or deleting a hot journal or WAL breaks recovery. Two processes opening the same database under different names use different journals, and WAL requires all processes on the same host. [inferred (search summary), https://www.sqlite.org/howtocorrupt.html]; [inferred (search summary), https://www.sqlite.org/wal.html] A developer-forums question about iCloud Backup restoring `.sqlite`, `-wal` and `-shm` inconsistently has no Apple reply (thread opened Apr 2022). [primary, https://developer.apple.com/forums/thread/704859]

### Inferences
- In the brief's design, text and FTS5 sit in a shared SQLite database while vectors sit in per-library memory-mapped files. That creates two consistency domains with no shared commit. A crash between the SQLite commit and the vector-file swap, or an iCloud Drive sync that delivers one file without the other, leaves the full-text and vector indexes disagreeing about which chunks exist. At minimum, each vector file needs a header with a generation number and the embedding-model id and dimension. The same generation must be recorded in SQLite in the transaction that commits the chunk rows, and the app must reconcile on open, rebuilding from SQLite when they differ (confidence: medium).
- Moving vectors into the same SQLite file (vec0, or a plain BLOB table scanned by the existing Accelerate code) would make text, FTS and vector updates one atomic commit, at the cost of the zero-copy mmap scan. Keeping vectors in a BLOB table and building an in-memory or float16 cache at open time is a middle path (confidence: medium).
- If any SQLite file (including `-wal` and `-shm`) lives in the ubiquity container or iCloud Drive, that directly contradicts Apple's "must never be stored in iCloud". It also risks the copy-without-WAL and multi-host WAL failure modes. Libraries synced through iCloud Drive should carry only source documents and immutable, versioned index artefacts, coordinated with `NSFileCoordinator`. Each device should then build its own local SQLite (and vectors), or sync structured state through CloudKit (`CKSyncEngine`). Vector files synced this way may be evicted or undownloaded placeholders on iOS until explicitly downloaded (confidence: medium-high on the Apple guidance; the app's actual file layout is unverified).
- A re-embedding migration fits this per-library layout well: build `library.v2.vec` alongside `v1`, dual-write new chunks, backfill, validate recall on a small golden set, then flip a pointer in SQLite and delete v1. The embedding-model id must be stored per file so that vectors from different models are never scanned together (confidence: medium).

### Gaps
- No current (2023+) Apple document restates the SQLite-in-iCloud prohibition. The explicit statement comes from the retired design guide, and the developer forums had no Apple answer on SQLite in iCloud Drive or iCloud Backup.
- sqlite.org's "How To Corrupt" and WAL pages could not be fetched, so the exact wording on file-sync services is from summaries.
- No published case study was found of an iOS app keeping a memory-mapped vector file and a SQLite FTS index in sync, or of the failure rates of iCloud Drive syncing such pairs.
