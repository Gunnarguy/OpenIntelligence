### retrieval

- RAGEngine.rerankWithCrossEncoder silently drops chunks instead of falling back. If tokenizing a query-chunk pair throws, the chunk is skipped (RAGEngine.swift:1434-1437, `catch { continue }`). If Core ML prediction throws, runPrediction returns nil and the chunk is never added to results (:1510-1512, and the collection loop after it). The heuristic fallback only fires when the model or tokenizer is nil (:330), so a model that loads but fails at inference returns fewer chunks, or zero if every prediction fails, and the query then has no evidence. Not reproduced; found by reading the code.
- Possible contributor to the nondeterminism in item 20 (low confidence). The cross-encoder scores are gathered from a TaskGroup in completion order and then sorted by score only (RAGEngine.swift:1545 and :1586-1588, after the max(0.01, ...) floor at :1585). Exact ties, such as duplicate chunk text, the uniform-0.5 case at :1560-1561, or several chunks clamped to 0.01, are therefore ordered by task completion, which can vary between runs. Lost-in-the-Middle in RAGService.swift:19751 also sorts by score with no tiebreak. The ledger says the reranker load race was fixed and determinism was still only 21%, so this is a hypothesis, not a diagnosis.
- AgenticOrchestrator.executeRecursiveResearch still has the fixed-size-cut-over-LiM composition that item 18 fixed only in executeDirectSynthesis. executeSearchStepWithChunks renders `chunks.prefix(10)` of the LiM-ordered array (AgenticOrchestrator.swift:1859). getResearchDecision, whose `.answer` branch returns the final answer, sees `currentContext.prefix(2000)` (:3088), which is about two chunks at up to 1000 characters each. executeForcedSynthesis cuts to `prefix(3500)` (:3189), and the accumulator keeps only `suffix(6000)` once past 8000 characters, discarding the initial search first (:3020-3021). For large result sets, rank 0 is at the LiM midpoint and may never reach the prompt. The code comment at :3744-3748 says this call site is the one that fires in Deep Think.
- AgenticOrchestrator.executeHonestSynthesis (AgenticOrchestrator.swift:1640) has no call site, and it still carries the hardcoded `String(searchResults.prefix(3000))` cut (:1653) that item 18 describes as replaced. It is dead code, which risks being reconnected with the old behaviour.

There are now 8 calls in AgenticOrchestrator.swift (:1078, :1845, :2187, :2454, :2572, :6533, :7844, :7865), plus one in RAGService's agentic precision lookup (RAGService.swift:8724). ### ingestion-2

- Streamed ingestion loses page rows (high confidence from reading, not run). SQLiteFullTextService.store(text:for:containerId:append: true) reads the existing text and then calls delete(for:) unconditionally (SQLiteFullTextService.swift:369-377). delete(for:) also runs DELETE FROM document_pages (:653-661). DocumentProcessor calls store before storePages on every batch (DocumentProcessor.swift:812-822). So after a >10 MB PDF streams in 15-page batches, document_pages probably holds only the last batch's pages. The only other code that writes pages is rebuildLocalSearchIndexesFromCanonicalState (RAGService.swift:7396-7511).
- Streamed ingestion reuses chunk keys (medium-high confidence). processDocument numbers chunks from 0 on every call (DocumentProcessor.swift:928-930, :5104) and adds no pageRange offset. importLargePDFStreamed stores chunk.metadata as is (RAGService+Streaming.swift:151, :179). So FTS5 chunk_id '<documentId>_<chunkIndex>' (SQLiteFullTextService.swift:864) repeats across batches. chunk_structured and chunk_table_rows use INSERT OR REPLACE keyed on chunk_id/row_id (:1026, :1066), so a later batch's table metadata can overwrite an earlier one's. The FTS-to-vector joins keyed documentId_chunkIndex (HybridSearchService.swift:1078, :1098; RAGService.swift:18370, :18391, :18508) can map a lexical hit to the wrong chunk.
- The token-limit splitter changes numbers. splitOversizedChunkByTokens splits on every '.', '!', '?' and newline (DocumentProcessor.swift:6603) and rejoins with '. ' (:6647). Decimals, version numbers, abbreviations and file names inside any chunk over 430 tokens are rewritten, for example '12.5' becomes '12. 5' and 'e.g.' becomes 'e. g.'. This changes embedded text and breaks exact numeric FTS matches, and oversized dense tables are the likeliest case. The unused splitOversizedChunk (:6536-6542) has the same split.
- Predictive self-tuning has no effect on window or overlap. Every buildChunkingPlan window is 280-420 and every overlap is 50-70 (AdaptiveEmbeddingOptimizer.swift:229-262), but DocumentProcessor clamps to 260/50 (DocumentProcessor.swift:877-881). Every auto-tuned import therefore chunks at 260/50, whatever the signals. The densePrecision preset's smaller 190-word target is replaced by the override's larger window (DocumentProcessor.swift:864 vs SemanticChunker.swift:258-259). The presets' maxSize (code 280, densePrecision 240) and parentWindowChars are also dropped, because DocumentProcessor always passes maxSize: safeMaxSize and no parentWindowChars (DocumentProcessor.swift:877-883).
- recommendChunkingPlan computes detectTechnicalDensity and analyzeSemanticComplexity and discards both with '_ =' (AdaptiveEmbeddingOptimizer.swift:179, :182). Its only structure signal is lines starting with '-', '*' or a digit (:185-190).
- StructuredDocumentParser.performTextRecognitionFallback (StructuredDocumentParser.swift:1418-1426) still sets minimumTextHeightFraction = 0.0, automaticallyDetectsLanguage = true and the full 13-language list. parsePageImage calls it at :731 and :774 without forwarding recognitionLanguages. So the 2026-08-30 OCR height floor and language narrowing do not reach the in-path fallback used for pages with no document structure or low parse quality.
- Table header loss after the token split: a structural table stays atomic up to maxAtomicWords = 380 (DocumentProcessor.swift:5288). That is above safeMaxSize 310 and likely above the 430-token limit for dense numeric content. The row splitter repeats the header (:6235-6238), but the later token splitter (:6597-6603) does not repeat the 'HEADERS:' line (:5822), so continuation parts can carry 'ROW n:' cells with no column labels.
- Page numbering in FTS5 document text and document_pages is built after empty pages are filtered out (DocumentProcessor.swift:791-793, then startPageNum + index + 1 at :799-800 and :817-818). A blank page therefore shifts every later page number down by one. Also, a batch or document with only one non-empty page stores no document_pages row (the 'count > 1' guard at :798 and :816).
- Code comment drift: OCRConfiguration.configureRequest's doc comment cites `recognitionLanguages(matching:)` (OCRConfiguration.swift:182-183), but the function is `narrowedRecognitionLanguages(matching:)` (:144).
