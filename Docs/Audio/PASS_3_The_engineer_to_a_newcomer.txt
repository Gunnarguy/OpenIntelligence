OpenIntelligence. Pass three. An engineer walks a newcomer through it.

You know the route now. This pass adds the numbers, the design decisions, where each stage runs, and what each stage quietly throws away. I am going to talk the way I would talk to a good engineer on their first week: assuming you can follow, but not assuming you know this codebase. Every number I say here was read from the source and is written down with its line in the full system trace document, so you can check any of them.

Section one. What happens when the app launches.

Less than you would think. The app struct wires two bridges so background work can talk to the ingestion and query services, configures tips, and on i O S registers five background task identifiers with the system: continued ingestion, continued query, index maintenance, Spotlight reindex, and app refresh. Then the root view constructs the service graph in one place, in order: workspace sync, the container service, StoreKit billing, the entitlement store, the RAG service, settings, model resolution, onboarding state, and what's-new state. The RAG service in turn builds the document processor, the embedding service, the vector store router, the context packer, and the extractive summariser.

Here is what does not happen at launch. The embedding model is not loaded; only its tokenizer is, because token counting is needed before any embedding. The full-text database is not opened; it opens on first use. The only model load at launch is the reranker, and that runs in a detached task with all compute units permitted. So the first query pays the cost of compiling the embedding model and opening the database, not the launch.

Two timers matter. Workspace changes are debounced two seconds before a sync pass. And there is a known defect: a timer in the workspace sync service fires every one point six eight seconds while the app is idle, because a container's orphaned state never resolves. It used to reload every vector store on every tick, which produced nearly three thousand loads in under three minutes of sitting still. The router now compares an on-disk signature first, so the tick is cheap. The tick itself is still there. That is the open item in the state file.

Section two. Ingestion, with numbers.

The queue is serial. One document at a time, always. Parallelism is inside a document: pages are extracted in a task group bounded by the device's Vision concurrency, and embeddings run in a task group bounded by the device's embedding concurrency. Both bounds come from a device capability ladder I will describe in section eight.

If the file is in iCloud and is only a placeholder, the app waits up to twenty seconds for it to download before reading. Files over five hundred megabytes that cannot be streamed are rejected outright, because loading them into a string would take up to two gigabytes.

Extraction for a P D F starts with text-layer validation. Take the page with the most native text, at least fifty characters. Render it. Run quick O C R on the render. If the native text is garbled compared with what Vision reads, route every page through O C R. Pages are rendered at three hundred and sixty D P I, which is the point size times five. On i O S that goes through U I Graphics Image Renderer with an opaque format; on mac O S it goes straight into a bitmap context, because the old path through N S Image produced images four times larger than requested and three hundred and seventy megabytes per page. Rendering is C P U work; it is not the bottleneck. On a real trace, render is twelve to sixteen milliseconds a page. A five-hour ingest is Vision recognition time, not rasterisation.

O C R is V N Recognize Text Request, accurate level, language correction on, and the recognition languages narrowed to the ones detected for this document. The structure pass is a different request, Recognize Documents Request, which reads rows and columns, and it runs at half resolution unless the page is flagged high risk. A complexity analyser decides that by rendering at one hundred and forty-four D P I and looking for grid lines and figures. Vision calls are throttled through an actor-based semaphore sized to the device, with a short cooldown between operations so G P U command buffers settle.

Audio is transcribed by S F Speech Recognizer with on-device recognition required, in segments of at most ten minutes. There is a newer Speech Analyzer code path in the source. It never compiles. It is behind a can-import check for a module that does not exist, and it calls an A P I shape the S D K does not declare. Every build takes the legacy path. That is a finding from this week, and it is the kind of thing you should expect to find in a codebase this size: a branch that looks live and is dead.

Chunking. The hard ceiling is three hundred and ten words. The largest target is two hundred and sixty. Overlap is capped at fifty. The smallest target is one hundred. Then the tokenizer check: the model accepts five hundred and ten tokens; eighty are reserved for the contextual prefix; so every chunk is validated at four hundred and thirty tokens using the real tokenizer, the same Rust-backed one the embedding provider uses. A chunk still oversized after splitting is logged and will be truncated by the model. Note the shape of that failure: it is logged, it is not counted anywhere a user sees.

Embedding. The default provider is Core M L with a Mini L M model producing three hundred and eighty-four dimensions. On i O S twenty-seven and mac O S twenty-seven, a Core A I provider becomes the default, loading the same model through Apple's newer compilation path; saved Core M L defaults are migrated to it automatically. Same vector space, same width. One inference is: tokenise, fill three pre-allocated input arrays of length five hundred and twelve, run prediction, mean-pool the token states under the attention mask, and L two normalise. Batches of more than four texts run in a task group with width equal to the device's embedding concurrency.

Which processor? The Core M L path sets compute units from the user's G P U execution profile. Efficiency and Balanced request C P U plus Neural Engine, deliberately excluding the G P U because the Neural Engine is the efficient unit for this. Performance and Maximum request all units. Core M L then places each layer. Until late August, Maximum requested C P U plus G P U, which excluded the Neural Engine and made the top profile slower than the one below it. The Core A I path exposes no placement control at all.

Persistence. Vectors go to a container's vector store: store batch, then persist, which writes the vectors file, the norms file and a metadata file atomically and re-maps the vectors. Then Spotlight, if enabled. Then the chunk rows go to F T S five. Then vocabulary and entity learning, then the optional document summary, one model call, then a second persist, then content tags. The document-level full text went to F T S five much earlier, inside extraction, before chunking. So there is a window where a document is lexically searchable at document level and absent from both chunk indexes. There is no transaction across the two stores. The restore path is what reconciles a crash in that window.

The full-text database has nine tables. Four are F T S five virtual tables: documents, chunks, document pages, and a vocabulary table. Five are ordinary tables for structured elements, table rows, document content, document metadata, and the semantic query cache. The chunks table indexes section title, section path, and content, tokenised with Porter stemming, and leaves the identifiers, page number and structure type unindexed. It uses write-ahead logging, and a busy timeout of three seconds so ingestion and a query touching the database together wait instead of failing.

Section three. The query, with numbers. Standard mode.

The chat screen builds an inference config from the settings and calls the RAG service's query method, which binds a stream handler and calls the internal query. The first thing the internal query does is ask the query runtime coordinator to resolve everything: quality mode, P C C eligibility, adaptive configuration, the query profile, and whether this run is agentic. If it is agentic, we leave for section five. Otherwise:

Step zero, the corpus vocabulary is fetched. Step one, optional model-driven query understanding if rewriting is enabled, then corpus-aware expansion and intent classification. Step two, the query is embedded with the same provider; a semantic cache hit skips this. Step three, hybrid search.

Hybrid search runs the vector search and the F T S five search concurrently. With the Standard initial top K of thirty, the vector side asks for ninety candidates, three times K, and the F T S side asks for the smaller of three times K and sixty. Structured rows get up to thirty-six. Fusion is reciprocal rank fusion with k equal to sixty, vector weight zero point five zero and keyword weight zero point five zero in a default library, nudged by the question's intent on this first pass, done off the main thread on a snapshot of the candidates so the document-frequency statistics are valid. After fusion, keyword-only hits that fell below the cut are re-attached, up to the larger of four and K over six, so an exact part-number match is never lost to paraphrase. Section title and path matches get a boost. Two later searches fuse differently. When retrieval looks weak, a cascade can search again leaning keyword, zero point three five and zero point six five, or zero point three eight and zero point six two, in a default library. And when the top match scores below zero point four five, a keyword retry can fuse at zero point three vector and zero point seven keyword.

Now the vector search itself, because this is where the G P U question is answered honestly. The vector store's search method has a threshold of one thousand. If the container has at least one thousand vectors, the G P U profile is performance or maximum, and a Metal device with a command queue exists, the memory-mapped buffer is handed to a Metal kernel with no copy; above a thousand documents a threadgroup kernel is used, otherwise a SIMD kernel. Below the threshold, on the efficiency or balanced profile, or without a G P U, it is C P U Accelerate: one matrix multiply over the mapped buffer if the count is at least the device's batch threshold, which is sixteen on M-series Macs, and one dot product per vector otherwise. Two things people get wrong: the user's G P U profile does gate this path, so on the default balanced profile vector search stays on the C P U, and the G P U path requires a compiled kernel, which can fail.

Step four, rerank. The reranker is a Core M L cross-encoder loaded with all compute units and low-precision G P U accumulation allowed. Query and passage are tokenised together to five hundred and twelve tokens and scored concurrently in a task group. It is called with top K times three and trimmed to that. Step four point three, the similarity floor: zero point two eight in Standard, zero point two five in Deep Think, zero point two zero in Maximum. Lenient mode lowers it; procedural questions raise it. Step four point four ensures more than one document is represented. Step four point five, M M R with lambda zero point six zero, zero point five five, zero point five zero by mode; the pairwise similarity matrix goes to Metal when there are more than fifty candidates, the profile allows Metal vector operations, and a G P U exists. Then parent retrieval, cross-reference resolution, and a targeted specification search. Then optional contextual compression, followed by a one-second sleep to let the Foundation Models rate budget recover.

Step five, context assembly. The budget is worked out for each question. Start from the window the device reports: four thousand and ninety-six tokens on the owner's iPhone and eight thousand one hundred and ninety-two on his Mac. Take away one hundred and twenty tokens, the system prompt, the question, and an answer reserve of one hundred and fifty to three hundred tokens. Keep eighty-eight percent of what is left, and turn it into characters at one point four characters per token, with a ceiling of ten thousand characters. On that iPhone it came to three thousand one hundred and ninety tokens, about four thousand four hundred and seventy characters. When the hybrid route can reach Private Cloud Compute, the first pass is sized for the cloud window the app assumes instead, a fixed thirty-two thousand seven hundred and sixty-eight tokens, keeping ninety-two percent, and if the answer then stays on the phone it is packed again to the phone's budget, keeping a safety reserve of two hundred and fifty-six tokens, the same reserve each Deep Think session keeps. Three thousand two hundred is the packing service's default, which its one caller overrides. A lookup gets its best passage first, and from five point seven whole, up to three fifths of the budget, then the sentences that match the question. Other questions get the strongest passages first and last. Chunks that do not fit are trimmed and their identifiers recorded.

Then the plan. Then generation. Then gates. Let me take the plan and the route together in section four.

Section four. Where the answer runs.

The planner produces one of four synthesis targets. Abstain when evidence is insufficient. Deterministic when an exact extracted value has nothing contradicting it, though no code asks for that today, so no plan is deterministic, and one would still run the model on the phone, with the extracted value able to replace the answer afterwards. Private Cloud Compute only when all of these hold: the capability snapshot allows it, the network is available, the app is in the foreground with the user present, or from five point seven an action can bring it forward to ask, or consent is already granted, the evidence as gathered, before it is shortened, fits the window the cloud reports, and either the local budget does not fit or the mode is Deep Think or Maximum and the answer draws on more than one document. Standard never goes to the cloud on difficulty alone. A new install starts on the hybrid setting, with permission set to ask when needed. Otherwise on device, with the reason recorded: network unavailable, consent unavailable, and so on. Every cloud plan carries an on-device fallback, and the plan has three stages: retrieve, deterministic; synthesise, the target; verify, deterministic.

The cloud payload is built by a minimiser before consent is asked: chunks in rank order, each cut to a character allowance of at least two hundred and forty. That truncation is silent in the payload. Consent is requested after retrieval, once the plan has selected the cloud and the payload exists. A denial forces on-device only. Always Allow is remembered, and after it the sheet no longer appears.

The route policy then maps the plan to a Foundation Models route. With a plan attached, the plan wins. Without one, the on-device window is read from the system model rather than assumed, and the cloud is chosen only if the estimate exceeds it. The cloud check itself requires Swift six point four, i O S or mac O S twenty-seven, the entitlement, and Apple's cloud model reporting available with quota remaining.

The session factory then creates the language model session. On device: the default system model, availability checked, and either a saved transcript resumed and prewarmed, or fresh instructions. There is an advanced on-device route in the code; it executes the default model, because the S D K exposes no advanced model, and it corrects the telemetry so no one is told a tier ran that did not. The cloud route creates Apple's Private Cloud Compute model with the same guards.

Generation is a streaming response with a temperature of zero point four in Standard, and a maximum response token count from settings. Deep Think and Maximum's calls use the temperature each step names, or the adaptive profile's, or zero point five. The on-device model's placement is Apple's decision; the app cannot move it.

Verification: nine gates, an actor, thresholds tau normal zero point four zero, tau touchy zero point five five for medical, legal, financial, safety and dosage categories, a margin of zero point zero three between the top two scores, though Gate A now reads the top score alone and nothing checks the margin, and a semantic grounding floor of zero point five zero. Gate E embeds the response and compares it to its best source; it is the one gate that costs an inference. The mode's overall confidence bar is zero point five zero, zero point six zero, and zero point eight zero; Maximum used to be zero point nine eight, and that was unreachable, so every Maximum answer failed. The gates label the answer once it is written. In Standard a failure holds the answer back only when the reliability setting is off or the overall score is under that bar, which is halved for a lookup, with a floor of zero point two five. Otherwise the answer shows, marked unverified, with its words unchanged, though the claims Gate B could not support drop off the fact-check list. Deep Think and Maximum answers get no gates in the shipped five point six, and from five point seven the gates only label them: verified only when all nine pass, with Gate A's floor raised to zero point four five in Deep Think and zero point five zero in Maximum. The mode's bar is read only on Standard's path, so it decides nothing for them.

Section five. Deep Think and Maximum.

In practice a run becomes agentic in two ways: the mode is Deep Think or Maximum, or the user pressed Go Deeper. A third way, the planner escalating a Standard query, is switched off while Apple's model writes the answers, and no other model ever writes them. Before the loop, a lookup can be answered straight from the source by the extractor, with no model call of its own and no checks. The orchestrator has four named profiles. Fast: two steps, stop at zero point seven zero confidence, escalate below zero point two five. Default: five steps, zero point eight five, zero point three five. Thorough: eight, zero point nine five, zero point four five. Unlimited: fifty steps, zero point nine eight, zero point five zero, with a comment in the source that says thermal will stop us first. Only Maximum uses one of them, unlimited. Deep Think takes its numbers from the device instead: five steps and zero point eight five on an A seventeen Pro, eight and zero point nine on an A eighteen, ten and zero point nine two on an A nineteen, and on the ultra tier twelve steps for each sixteen gigabytes of memory, never fewer than twelve and at most thirty-two, with zero point nine five. The ultra tier is a Mac with an M one Ultra or an M two or later, an iPad Pro with an M two or later, and an iPhone with an A twenty or later.

First, a planning call to the model on the phone decides whether documents are needed. Then up to five search phrasings each go through the full search pipeline, and the results are merged into twenty passages. Retrieval quality is then graded. Lexical relevance under zero point one zero with a bad semantic match is a hard exit. Cross-references the passages mention can add a few more, and the pool is graded again. Only an excellent or good grade goes on to a chain of sessions. A moderate one gets a single write-up, and a low one first gets three quick candidate answers on the phone, the best of which is the answer when it scores high enough. The chain cuts every window from those twenty passages before the first session, four passages a window on a four thousand and ninety-six token window, so it never searches again. The chain's configuration names three, four, five or fifty sessions as starting lengths, but Deep Think runs at most eight sessions on every device, and fewer when the windows run out: five for twenty passages. Each session is one model call with tools off, tried up to twice more if the prompt overflows or the call fails for a moment. It stops when the windows run out, or from the fifth session when confidence, coverage of the question's parts and the lack of anything new all hold at once, or when the model writes answer complete, or when a session still fails after its retries, and then its last finding is the answer. Between sessions it carries its earlier findings, up to one thousand two hundred characters, instead of the transcript, because the transcript is what overflowed at four thousand five hundred and twenty-one tokens on a four thousand and ninety-six limit. After the chain, recursive research can search again, with a wall-clock budget of one hundred and eighty seconds and a per-call iteration cap. There are two call sites: one passes five iterations, the other three, and the only way to tell which ran from a log is the denominator in the iteration counter. Maximum's unlimited loop reads three unread passages a session, scales its session cap to the evidence pool at three chunks per session, disables tools inside sessions to prevent overflow, and stops when it is zero point nine eight confident and has covered the question's parts, when it has found nothing new after five sessions, at the cap, or after three failures in a row. It never searches again.

Every session and every planning and analysis call is pinned to the device, unless Private Cloud Compute is chosen in the model picker, which lifts that pin. Under the hybrid setting only the write-ups go through the plan and may reach the cloud.

Section six. What each stage silently drops.

This is the failure class this codebase keeps producing: a stage discards data and every log line still reads healthy. So here is the list.

Extraction drops files over five hundred megabytes, duplicates, files past quota, low-confidence O C R strings, and uncertain numeric table cells. Chunking drops the tail past five hundred and ten tokens on chunks still oversized after splitting. Persistence can leave vectors without chunk rows after a crash between the two writes. Retrieval drops candidates below the similarity floor, chunks judged redundant by M M R, chunks that do not fit the budget, and siblings skipped for budget. The cloud payload cuts each chunk to its allowance. Generation can be refused by Apple's guardrails. Verification removes uncited and ungrounded claims. Of all of those, only the retrieval drops and the verification removals are visible in the app; the rest are in logs and the stage ledger. When you are looking for a bug, ask what each stage dropped before you ask what it computed.

Section seven. i O S versus mac O S.

Background tasks are registered on i O S only. Live Activities are i O S only. P D F rendering uses different code on each platform. The G P U buffer pool listens for memory warnings on i O S only. Camera capture and the three-D atlas use full-screen covers on i O S and sheets on mac O S. The platform seam in this codebase is almost always a can-import U I Kit check with an else branch, and the else branch, the Mac branch, is historically where the worse or missing implementation lives. It still builds, and it still logs healthy.

Section eight. The device ladder and the hardware map.

At first access, the device capability service reads the device model, the C P U brand string on Mac, physical memory, and a Metal device query for G P U limits, and classifies the device into a tier: baseline for A seventeen Pro, enhanced for A eighteen, advanced for A nineteen, ultra advanced for a Mac with an M one Ultra or an M two or later, an iPad Pro with an M two or later and an iPhone with an A twenty or later, unsupported for anything without Apple Intelligence. M one Macs and the M one iPads are enhanced. From the tier and memory it derives everything else: agentic step concurrency from three to thirty-two, step cooldown from one hundred milliseconds to zero, vector batch size from one hundred and twenty-eight to sixteen thousand three hundred and eighty-four, embedding batch from eight to five hundred and twelve, Vision concurrency from two to sixty-four, P D F render concurrency from one to sixty-four capped by a per-page memory estimate, and embedding concurrency from two to one hundred and twenty-eight. The first two are never applied: the step concurrency is only printed in a diagnostic summary, and nothing calls that agentic step cooldown. A different cooldown, the pipeline optimiser's, does run: before each Standard answer it waits two hundred milliseconds on an A seventeen Pro, down to none on the ultra tier, and longer when memory is critically low or the phone is critically hot.

The user's G P U execution profile sits on top: efficiency, balanced, performance, maximum. It sets the Core M L compute units for the query-side models and the ingestion embedder, whether Metal may be used for the M M R matrix and for vector search, and the concurrency ceilings. Only performance and maximum let either one use Metal.

Thermal and memory: critical thermal switches the pipeline to minimal mode; critical memory pressure switches to efficient mode; serious thermal no longer throttles. Minimal mode's rule of no agentic steps is a value nothing reads, so Deep Think and Maximum still run when the phone is hot. Neither loop reads the heat, the memory, the battery or Low Power Mode, and the battery lowers no work in any mode. The app has no way to measure Neural Engine utilisation, because there is no public A P I for it; the hardware display's Neural Engine pulse is synthetic.

And the complete list of places the app requests a processor: the embedding model, the reranker, the Y O L O detector, the region detector, the document classifier, and a dormant extractive Q A model, all through Core M L compute units. The Metal kernels for similarity, normalisation and M M R. Accelerate for everything below the G P U threshold. Everything else, Vision, Speech, Natural Language, and the language model itself, is framework-decided.
