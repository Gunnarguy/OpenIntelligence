### Added
- **[Ingestion]** **JSON, JSON Lines and NDJSON import as records.** Through 5.6 a `.json` file took the code-file lane and `.jsonl` and `.ndjson`, as unknown extensions, took the plain-text lane: each came in as its text as written, cut wherever the chunker's word window fell. `.jsonl` could not be chosen in either picker (its system type is dynamic and conforms only to `public.data`, measured on macOS 27); `.ndjson` could, as `public.text` (roadmap row 3f449a74d54f8199b1fce61c8ff6af0d). `JSONRecordExtractor` reads one record per line of JSON Lines, per element of a top-level array, and per object or list member of a top-level object, and writes each as a `Record N of T` header with one `path: value` line per value. It has its own reader (`JSONValue.parse`), because `JSONSerialization` loses three things a stored passage should keep: members stay in the file's order, a number keeps the file's digits (`12.50` is not rewritten `12.5`), and members with the same name are all kept. A null or empty member is written `null`, `""`, `[]` or `{}`, so its name is not lost. A line that is not JSON is kept as a record holding the line as written, and the count is logged. `processDocument` cuts one passage per record out of the cleaned text; when the headers do not all survive cleanup it logs a warning and chunks the text as prose, so the fallback loses boundaries and no text. A record over the embedding limit is cut at its own field lines, and every part starts with `Record N of T, part K of M`. A leading byte-order mark is taken off, and JSON Lines is split at line feeds only, since JSON allows other separator characters raw inside a string. A file that does not parse, a JSON Lines file over 64 MB and a `.json` file over 16 MB take the text lane as before; the 16 MB figure is a guess at what a phone can hold as one parsed tree and has not been measured. `.jsonl` and `.ndjson` are stored as `DocumentType.json`, so no stored type changes. Both pickers name the two extensions, and the import review no longer calls `.json` reduced-fidelity; a `.json` that falls back to the text lane says so only in the log. `[evidence_level: test_verified, confidence: high; evidence_source: JSONRecordExtractorTests (15 cases) and five IngestionFormatCoverageTests cases that drive real files through processDocument, one of them a single record far over the embedding limit; the full suite on an iOS 27.0 simulator on 2026-10-09 from a copy of the tree made outside iCloud: 670 tests, 0 failures, 3 skipped (the two EmbeddingProviderAgreementTests and LayoutReadingOrderTests' interleaved-stream case, which skip themselves)]` Not seen on a device: no `.jsonl` has been picked in the iOS document picker and no question has been asked against an imported record.

- **[UI]** **The camera names arbitrary objects and boxes them, which Vision has no request for.** Pointing it at a kitchen previously produced the chips "Structure, Wood Processed, Furniture" and not one box, because the only Vision requests that return a **labelled** box are people, faces, cat/dog, barcodes and text. `ClassifyImageRequest` knows roughly a thousand categories and has no spatial extent at all: it describes the whole frame. - **[UI]** **The live camera overlay was wrong in four independent ways, and the first one made every box meaningless.** Enabling the screen exposed it; the owner's verdict on first sight was that it looked like shit, which it did. **1. Nothing ever told AVFoundation or Vision which way is up.** No `videoRotationAngle` on any connection and no `CGImagePropertyOrientation` on any request, anywhere in the repository. Buffers arrive in sensor orientation, so a portrait-held phone fed Vision an image rotated a quarter turn: normalized X ran down the screen and Y ran across it, every box was transposed with width and height swapped, and text recognition, which tolerates skew but not 90 degrees, mostly returned nothing. `AVCaptureDevice.RotationCoordinator` now drives the connection's angle and re-applies it via KVO as the device turns, so the buffers themselves arrive upright and every consumer benefits rather than each request needing a hint. **2. Every box was a new view every frame.** `DetectedRegion` declared `let id = UUID()` and the regions are rebuilt per frame, so `ForEach` saw a wholly new identity set each update and SwiftUI destroyed and recreated every box. The two `interpolatingSpring` animations written against those views could never run, because a spring interpolates a surviving view and none survived; `smoothDocumentRegions` was defeated the same way. The boxes were not jittering, they were strobing. `RegionIdentityTracker` now carries identity across frames by intersection-over-union within a type. **3. The coordinate transform ignored the preview's crop.** Five identical copies of `minX * containerSize.width` stretched Vision's normalized space onto the view's bounds, while the preview layer is `.resizeAspectFill`, which scales the image to cover and crops the overflow. On a 1920x1080 buffer shown portrait roughly 18% of the image width is off-screen, so boxes were compressed by about 0.82 and pulled toward the centre, worsening toward the edges. Because aspect-fill crops symmetrically the centre stayed correct, which is why it read as intermittently wrong rather than always wrong. All five now call one tested function. **4. The throttle was in dead code.** `analyzeFrame`, which carries the 10 FPS guard, barcode detection and a text-height floor, has **zero call sites**; the live path is `performFrameAnalysis`, which ran eight Vision requests synchronously on the serial analysis queue for every delivered frame, each followed by a GPU drain and a sleep, while AVFoundation silently dropped the backlog with no `didDrop` implementation to notice. The guard now sits on the path that runs. Also removed an empty `Task { @MainActor in await MainActor.run { } }` that cost a task allocation and two main-actor hops per frame to do nothing. 15 tests over the geometry and the tracker, including one that asserts the new transform **disagrees** with the old naive one away from the frame centre, so deleting the aspect compensation fails a test rather than silently restoring the defect. `[evidence_level: test_verified, confidence: high, not_device_verified, evidence_source: CameraOverlayGeometry.swift, CameraOverlayGeometryTests.swift 15 cases; AVCaptureDevice.h RotationCoordinator and AVCaptureSession.h isVideoRotationAngleSupported in iPhoneOS27.0.sdk; zero repo-wide grep hits for CGImagePropertyOrientation and videoRotationAngle before this change]`

### Changed
- **[Orchestration]** **Generation settings can now follow what the question is asking for, instead of one temperature per quality mode.** `RAGQualityMode` carries a single temperature for every question asked in that mode, so Standard answered a serial-number lookup and an open-ended comparison identically at 0.4. The answer intent is a better signal and `QueryEnhancementService` has already resolved it before generation. `FoundationModelDynamicProfileRegistry` maps it to one of four profiles: extractive for lookups, table lookups **and calculations** (0.10 / 400 tokens, because a derived number has one right answer and sampling variance in arithmetic is a wrong total rather than creativity), grounded for procedures (0.30 / 900), analytical for comparison and investigation (0.35 / 1400), summarization (0.40 / 1000). **The registry existed before this and was a placeholder that would have made answers worse.** It mapped each intent to a complete replacement `systemPrompt`, one-line strings such as "You are a helpful assistant", which would have substituted a generic sentence for the grounding, citation and abstention rules `FoundationModelPromptCompiler` assembles. It had zero call sites and `SettingsView` had already pulled "Dynamic Profiles" from the capability list as a false claim. It now produces generation parameters only and touches no prompt. **Off by default and opt-in**, in Model Parameters, because the effect on answer quality is unmeasured and currently unmeasurable here: retrieval is nondeterministic, two runs of one build return different evidence, so no A/B in this repository is trustworthy yet, and shipping it on would change everyone's answers on a hypothesis. `UserDefaults.bool(forKey:)` is false for an absent key, so nothing changes for an existing install. Applying a profile is a pure function returning a modified copy and **writes nothing back to settings**, unlike `AutoTuneService`, which adjusts the same two values by persisting them over what the owner set by hand and survives turning the feature off; it has zero call sites and a test now pins that this one does not behave that way. **It applies to Standard only.** Deep Think and Maximum return earlier via `executeAgenticQuery`, which never reads this config for generation: it builds `optimizedConfig` from `qualityMode.agenticConfig` and hands that to `AgenticOrchestrator`. The first version of this change applied the profile above that branch, which mutated a local the agentic path never reads while logging `temperature 0.4 -> 0.35` as though it had taken effect. A log asserting a change that did not happen is worse than no feature, so the gate now sits below the branch and the limit is stated rather than papered over. Reaching the agentic path means changing where `AgenticOrchestrator` gets its generation parameters, tracked separately. 10 tests. `[evidence_level: test_verified, confidence: high, evidence_source: FoundationModelDynamicProfileRegistry.swift, RAGService.swift adaptive gate, AdaptiveInferenceProfileTests.swift]`
- **[Ingestion]** **Vision's data detection was being computed and thrown away, and five regexes were used in its place.** `RecognizeDocumentsRequest` runs data detection in the same pass that produces the transcript and hands the results back on `DocumentObservation.Container.Text.detectedData`. `StructuredDocumentParser.extractDetectedData` read none of it: it took the `Text` value, used only `.transcript`, and re-derived entities from hand-written patterns, under a comment saying full integration "requires additional API verification". That verification is done, against `DataDetection.swiftinterface` in the iOS 27 SDK. The patterns matched email addresses, **US-format** phone numbers, `http(s)` URLs, **three** currency symbols and two numeric date shapes, so a European invoice yielded no amounts and a postal address was invisible. Apple's detector returns ten categories including postal addresses split into street, city, state and postal code, calendar events as real `Date` values, money as a `Decimal` plus a `Locale.Currency`, measurements, flight numbers, shipment tracking numbers and payment identifiers. It also returns **parsed values rather than matched substrings**, so `DetectedEntity` now keeps both: `value` is the normalised form and `rawText` is the text as printed, because a reader may search for either. The regexes are kept rather than deleted and run only for the types Apple returned nothing for, because `detectedData` is empty whenever the parse degraded to plain text recognition, which is exactly the low-quality scan where one email address may be the only thing worth extracting. **A stated limit:** this function is called from `parseTable` only, so entities still come from table cells and not from paragraphs; closing that gap touches several element-construction paths and is tracked separately. `[evidence_level: build_verified, confidence: high, evidence_source: StructuredDocumentParser.swift extractDetectedData/entity(from:in:)/patternEntities; Docs/INGESTION_PIPELINE.md §2.7]`

### Fixed

That is what made the screen read as confusing: three controls that move, save, and change nothing, under a sentence insisting they do. **The sliders are deliberately kept**, which a comment in that file has documented since before this change: their consumer, `LocalOpenAIServerLLMService`, is scaffolding for the roadmap row "Bring-your-own local model on Mac (third-party model host)", which is still open, and deleting the controls would delete a planned feature's UI. - **[Infrastructure]** **The test suite could not build, and the cause recorded for it was wrong.** `xcodebuild test` failed to link `OpenIntelligenceEngine.framework` with every `Tokenizers` symbol undefined. The explanation written into `Docs/ai/STATE.md` and the roadmap on 2026-09-10, that the Engine target declared no `packageProductDependencies`, was false and came from an inspection regex capped at 1200 characters that truncated the target block before reaching the declaration.
