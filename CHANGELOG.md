- **[Orchestration]** **The source-only check's first call could write until the model's context overflowed.** The draft call passed no `maximumResponseTokens`, and Apple documents that the model may then produce "the longest answer its context size supports" and throw if it does not stop (developer.apple.com, `GenerationOptions.maximumResponseTokens`, read 2026-09-23). The 163.8 s run above spent 163.5 s in that call and ended in "The session's transcript exceeded the model's context size". The draft now has a 1,024-token limit (`draftTokenLimit`); a structured response that reaches a limit throws a parse error at once (probed 2026-09-23: 0.9 s at a 30-token limit), which `verifyAndRender` already treats as "keep the generated answer". The limit was first set to `draftOutputReserve`, the 700 tokens the prompt budget reserves, and review asked whether that cut legitimate drafts. It did: on three Deep Think lookups the same day, completed drafts used 571 and 675 of 700 tokens and the third failed to parse, most likely at the limit. 1,024 is about 1.5 times the largest completed draft and still well short of the overflow. Each completed draft logs its use (`[SourceOnly] Draft used N of 1024 output tokens`), and every exit of the check logs its duration and outcome (`[SourceOnly] Finished in …`, `[SourceOnly] Applied: …`). In those three runs the check took 22.8 to 32.6 s and changed none of the answers. `[evidence_level: measured+doc_verified, confidence: high_for_these_runs]`

The real cause is a level deeper: `OpenIntelligence/swift-transformers` is a **shim** whose entire source is `@_exported import Tokenizers`, and the module it re-exports comes from a separate remote package, `swift-tokenizers` 0.7.1. Four Engine sources import `Tokenizers` directly, so their symbols live in a framework Xcode builds and leaves unused in `PackageFrameworks/`, because Xcode links a product's transitive package dependencies into an **application** target and not into a **framework** target. That is why the app, the simulator smoke build and Xcode Cloud were all unaffected: the test bundle is the only thing that links the Engine as a standalone unit. Wiring only the Engine moved the failure rather than fixing it, because declaring the product explicitly anywhere turns off the automatic inference the app had been relying on, so both targets now declare it. `scripts/fix_engine_tokenizers_link.py` performs and documents the edit, and reads the target block with no character cap, deliberately. `[evidence_level: build_verified, confidence: exact, evidence_source: full Ld command lines before and after; Tokenizers_<hash>_PackageProduct.framework present in PackageFrameworks and absent from the Engine link line]`
